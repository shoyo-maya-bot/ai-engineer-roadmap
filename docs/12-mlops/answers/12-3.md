```markdown
# 配備の手順（手元の PC）

## 用意するもの
- Docker と compose（メモリ 16 GB の PC。GPU なし）

## 戻し方
- git で前のコミットに戻し、手順 2 をやり直す

## 止め方と消し方
- 止める: docker compose down
- 消す: docker compose down -v（記録とモデルも消える）

## 監視
- 毎朝 p12_monitor を流す（12-4）
```

再起動の確かめ:

```bash
# PC（または Docker）を再起動した後
docker compose ps                  # agent と ollama が Up
curl -s localhost:8000/healthz     # {"status": "ok", ...}
```

なぜこう書くか:

- 「用意するもの」に、メモリとモデルを書きます。動かない原因の多くは、メモリに載らないモデルを選んだことです（09-3）
- `restart: unless-stopped` は、`docker compose down` や `stop` で止めたときは立ち上げ直しません。止めたいときに止められます
- 「戻し方」と「止め方と消し方」は、問題が起きてから考えると慌てます。動かす前に書いておきます

## 2 2 台で動かすと

起きること:

1. 質問（`POST /ask`）を台 1 が受け、承認待ちの状態を台 1 のファイルに書いて `202` を返す
2. 承認（`POST /approvals/<id>`）を、負荷を分ける仕組みが台 2 に回す
3. 台 2 のフォルダには状態が無いので `404`。承認の係には「承認待ちの依頼が見つかりません」と返る

置き場所の案:

| 案 | 内容 |
|---|---|
| データベース | 状態を JSON のまま 1 行に入れる表を作る。どの台からも読める |
| 同じ依頼は同じ台へ | 負荷を分ける仕組みで、`request_id` ごとに同じ台へ回す。台が落ちると状態も失われる |

テスト（`test_p12_api.py` の `make_app`・`call` などを使う）:

```python
def test_two_instances_need_a_shared_store(tmp_path: Path) -> None:
    tracker = MemoryIssueTracker()
    first = make_app(tmp_path / "a", [search("延長 回数"), file_issue()], tracker)
    second = make_app(tmp_path / "b", [say("起票しました")], tracker)  # 別のフォルダ = 別の台
    _, body = call(first, "POST", "/ask", {"question": FILE})
    path = f"/approvals/{body['request_id']}"
    assert call(second, "POST", path, {"approved": True}, token=TOKEN)[0] == 404
    second.store = first.store  # 同じ置き場所を見るようにする
    status, body = call(second, "POST", path, {"approved": True}, token=TOKEN)
    assert status == 200 and [i.title for i in tracker.issues] == ["延長の回数が資料に無い"]
```

差し替えるときにテストで確かめること:

- 別の台（別の `AgentApp`）が保存した状態を、もう一方の台が読めて、承認を続けられること（上のテスト）
- 承認が済んだら状態が消え、2 回目の承認は `404` になること（二重に承認しても、起票が 2 件にならない）
- 同じ依頼に 2 つの承認が同時に来たとき、1 つだけが通ること（データベースの仕組みで守る。ファイルの版では確かめていない）

## 3 B の置き方の月の費用

1 日 200 件・月 20 営業日・1 件あたり入力 約 2,400・出力 約 100 トークンとすると:

```text
月のトークン: 入力 2,400 × 200 × 20 = 9,600,000 / 出力 100 × 200 × 20 = 400,000
月の費用    : 9.6 × 入力の単価 + 0.4 × 出力の単価（単価は 100 万トークンあたり）
```

```python
from roadmap_examples.p07_cost import Price, cost

price = Price(input_per_million=..., output_per_million=...)  # 公式の料金ページで確かめた単価を入れる
monthly = cost(2_400 * 200 * 20, 100 * 200 * 20, price)
```

見積もりに足すもの:

- 評価を流す分（07・10・11 の評価セットを、モデルやプロンプトを変えるたびに流す）
- 頼み直し（07-2 の形の誤り）や、上限で止まった依頼の分。記録（12-4）の実際のトークンで見直す
- 入力が出力よりずっと多いので、入力の単価が費用を左右します。資料を短く渡す（08 のチャンクの大きさ・件数）と効きます
