# 12-2 解答

[12-2 Docker と CI/CD](../12-2-docker-cicd.md) の演習の解答の一例です。

## 1 組み立てて動かす

```bash
cd examples
docker build -t roadmap-agent .
docker run -d --name agent -p 127.0.0.1:8000:8000 -e AGENT_MODEL=example-model \
    -e OLLAMA_BASE_URL=http://127.0.0.1:9 roadmap-agent      # わざと繋がらない場所を指す
curl -s localhost:8000/healthz
curl -s -w ' %{http_code}\n' localhost:8000/ask -H "Content-Type: application/json" -d '{"question": "備品は何日間借りられますか？"}'
docker exec agent cat /app/var/requests.jsonl
docker exec agent id
docker rm -f agent
```

手元で流したときの出力です（`request_id`・時刻・版は毎回変わります）。

```text
{"status": "ok", "model": "example-model", "prompt_version": "c38ba71049a8"}
{"request_id": "...", "status": "error", "answer": "", "error": "いまは答えられません。しばらくしてから、もう一度送ってください"} 503
{"time": "...", "endpoint": "/ask", "status": "error", "latency_ms": 14.4, ..., "findings": ["モデルを呼べませんでした（URLError）"], "trace": []}
uid=1000(agent) gid=1000(agent) groups=1000(agent)
```

なぜこう確かめるか:

- `/healthz` はモデルを呼ばないので、Ollama が無くても `200` です。「API は動いている」と「答えられる」は別に確かめます
- 繋がらないときの `503` と記録は、本番でいちばん起きやすい失敗です。起きたときに記録で分かることを、先に確かめておきます
- `id` で、root ではないユーザー（`agent`）で動いていることも確かめています

## 2 `COPY . .` にすると起きうること

| 起きうること | 理由 |
|---|---|
| 秘密や個人情報がイメージに入る | `.dockerignore` から `.env` や `var/` の行が消えたとき、`.env` の鍵や、記録（`requests.jsonl`）・起票先がイメージに入る |
| 組み立てが遅くなる | どのファイルを直しても `COPY` の層が変わり、その後の `uv sync` が毎回やり直しになる |
| イメージが大きくなる・壊れる | テストやキャッシュも入る。`.dockerignore` が無ければ、手元の `.venv`（その PC 用）まで入って、中の仮想環境と食い違う |

なぜ避けるか:

- `COPY` するものを並べておけば、何がイメージに入るかを Dockerfile を読むだけで確かめられます
- `.dockerignore` は「入れないもの」の一覧で、書き忘れると入ってしまいます。入れるものを並べる書き方と両方使うと、守りが 2 重になります

## 3 compose で承認の流れを通す

```bash
cd examples
docker compose --env-file ../.env up --build -d
docker compose exec ollama ollama pull <ツールに対応したモデル名>

curl -s localhost:8000/ask -H "Content-Type: application/json" \
    -d '{"question": "備品を買うときの承認の流れを教えてください。資料に無ければ課題にしてください。"}'
# → 202 なら {"request_id": "<id>", "status": "waiting_approval", "approval": {...}} が返る（モデルが起票を選ばなければ 200 で答える）

curl -s localhost:8000/approvals/<id> -H "Authorization: Bearer <.env の APPROVER_TOKEN>" \
    -H "Content-Type: application/json" -d '{"approved": true}'

docker compose down && docker compose --env-file ../.env up -d
docker compose exec agent cat /app/var/requests.jsonl      # down の前の記録が残っている
```

なぜこう確かめるか:

- `down` はコンテナを消しますが、名前付きのボリューム（`agent-data`・`ollama`）は残ります。記録と、入れたモデルが消えないことを確かめています
- ボリュームまで消すのは `docker compose down -v` です。記録を消してよいときだけ使います
- モデルが起票を選ぶかは、モデルとその時の答えしだいです。`202` にならなければ、質問を変えるか、12-1 のテストのように台本で流れを確かめます

## 4 テストが通ってから組み立てる

```yaml
jobs:
  guard-tests:
    runs-on: ubuntu-latest
    timeout-minutes: 10
    steps:
      - uses: actions/checkout@v7
        with:
          persist-credentials: false
      - uses: actions/setup-python@v7
        with:
          python-version: "3.12"
      - run: pip install "uv==0.8.17"
      - working-directory: examples
        run: |
          uv sync --locked
          uv run --frozen pytest
  build:
    needs: [guard-tests] # 守りのテストが通ったときだけ動く
    runs-on: ubuntu-latest
    timeout-minutes: 20
    steps:
      - uses: actions/checkout@v7
        with:
          persist-credentials: false
      - working-directory: examples
        run: docker build -t roadmap-agent:${{ github.sha }} .
      # 起動の確かめは本文の例と同じ
```

なぜこうするか:

- `needs` を書くと、前のジョブが成功したときだけ次のジョブが動きます。テストに落ちたコードのイメージは作られません
- この教材のリポジトリの `ci.yml` でも、公開（`deploy`）は、検査とテストのジョブすべてを `needs` に並べています
