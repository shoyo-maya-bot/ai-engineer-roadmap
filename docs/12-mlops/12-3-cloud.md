# 12-3 クラウドへの配備

!!! abstract "到達目標"
    - AI アプリを配備するときに決めること（動かす場所・LLM の置き場所・秘密・入口の守り・台数・記録の置き場所）を挙げられる
    - 費用のかからない配備（自分の PC やサーバーで compose）と、費用のかかる配備（クラウドのコンテナの実行サービス）を比べて選べる
    - クラウドに置くときの、費用の上限・止め方・消し方を、配備の手順書に書ける

## 何か

**配備**（デプロイ）は、作ったアプリを、使う人が呼べる場所で動かすことです。
クラウドでアプリを動かす方法は、大きく 3 つあります。どの事業者にも、似た名前のサービスがあります。

| 方法 | 何を借りるか | 手間 | 費用のかかり方 |
|---|---|---|---|
| 仮想マシン（VM） | OS ごと 1 台 | OS の更新・Docker の用意も自分で | 動かしている時間（止めてもディスクの料金は残ることが多い） |
| コンテナの実行サービス | イメージを渡すと動かしてくれる | 少ない。台数を呼ばれた分だけ増減できるものが多い | 呼ばれた時間や回数。0 台まで減らせるものもある |
| Kubernetes などの基盤 | コンテナを並べて動かす仕組み一式 | 多い。大きなシステム向け | 基盤の分 + 動かした分 |

AI アプリでは、もう 1 つ決めることがあります。**LLM をどこで動かすか** です。

| 置き方 | 費用 | 向いている場面 |
|---|---|---|
| A: 手元や社内のサーバーで、Ollama と API を一緒に動かす（12-2 の compose） | 電気代とサーバーだけ（API の料金は 0） | 社内の少人数・試験運用・データを外に出せない |
| B: API はクラウド、LLM はクラウドの API を呼ぶ | トークンに応じた従量課金（07-4） | 利用が増減する・大きなモデルが要る |
| C: API も Ollama も、クラウドの GPU つきの VM で動かす | GPU の時間課金（使っていない時間もかかる） | 自分のモデル（09）を動かしたい・利用が多く一定 |

この教材の演習は A で進めます。B と C は費用がかかるので、任意です。

## なぜ必要か

配備すると、使う人が増え、動かし続ける時間も長くなります。そのぶん、手元では気にしなかったことが問題になります。

- **費用**: クラウドは、消し忘れたものにも料金がかかります。GPU つきの VM を止め忘れると、使っていない間も課金が続きます
- **入口**: インターネットに開いた API は、誰でも呼べます。質問の API を誰でも呼べれば、LLM の費用を他人に使われます。承認の API なら、勝手に承認されます
- **状態**: 12-1 の API は、承認待ちの状態と記録をファイルに書きます。台数を 2 台に増やすと、別の台が書いたファイルは見えません
- **秘密**: 承認の鍵や API のキーを、イメージや手順書に書いてしまうと、見た人が使えてしまいます

配備の前に、これらを決めて手順書に書いておきます。手順書は 13 の提出物の 1 つです。

## どうやるか

### 配備の前に決めること

| 決めること | 12 の API での答え（A の場合） | 理由 |
|---|---|---|
| 動かす場所 | 社内の 1 台のサーバー（または手元の PC）で compose | 費用がかからない。データを外に出さない |
| LLM の置き場所 | 同じ compose の Ollama | API の料金は 0。モデルはメモリに入る大きさを選ぶ（06-4・09-3） |
| 台数 | 1 台 | 承認待ちの状態がファイルなので、1 台にそろえる（下の「状態の置き場所」） |
| 秘密 | `.env` に書き、compose が環境変数で渡す | イメージにもリポジトリにも入れない |
| 入口の守り | `127.0.0.1` だけで待ち受け、社内に開くときは前段に認証つきの入口を置く | 質問の API には、今は認証が無い |
| 記録の置き場所 | ボリューム（`agent-data`） | 作り直しても消えない。監視（12-4）で読む |
| 止め方・消し方 | `docker compose down`（ボリュームも消すなら `-v`） | 手順書に書いておく |

### 設定は環境変数で渡す

同じイメージを、手元・試験・本番で、設定だけ変えて動かせるように、設定は環境変数で渡します。12-1 の API は、コマンドの引数が無ければ環境変数を読みます（記録の置き場所 `AGENT_DATA_DIR` も同じです）。

<!-- src: examples/src/roadmap_examples/p12_api.py -->
```python title="examples/src/roadmap_examples/p12_api.py"
env = os.environ
p = argparse.ArgumentParser(prog="p12_api", description="ガードレールつきのエージェントを HTTP の API にする")
p.add_argument(
    "--model", default=env.get("AGENT_MODEL"), help="ツールに対応した Ollama のモデル名（環境変数 AGENT_MODEL）"
)
p.add_argument(
    "--base-url", default=env.get("OLLAMA_BASE_URL", DEFAULT_BASE_URL), help="Ollama の場所（OLLAMA_BASE_URL）"
)
```

承認の鍵（`APPROVER_TOKEN`）も環境変数です。クラウドでは、秘密を預かる仕組み（シークレットの管理）に鍵を置き、そこから環境変数として渡すのがふつうです。

### 無料の道: 自分のサーバーで動かし続ける

12-2 の compose を、社内のサーバーや、いつも電源の入っている PC で動かします。サーバーを再起動しても動くように、`restart` を足します
（[公式ドキュメント: compose の services](https://docs.docker.com/reference/compose-file/services/)）。

例: `compose.yaml` の `agent` と `ollama` に足す行

```yaml
    restart: unless-stopped # 止めるまでは、落ちても再起動しても立ち上げ直す
```

社内のほかの PC から使えるようにするときは、API の前に、認証と暗号化（HTTPS）をする入口（リバースプロキシ）を置きます。
12-1 の API の質問の入り口には認証が無いので、そのまま社内に開くと、誰でも LLM を使えてしまいます。

### 状態の置き場所と台数

12-1 の API は、承認待ちの状態をファイルに書きます（10-2 の考え方）。

<!-- src: examples/src/roadmap_examples/p12_api.py -->
```python title="examples/src/roadmap_examples/p12_api.py"
    def save(self, request_id: str, question: str, state: AgentState) -> None:
        self.folder.mkdir(parents=True, exist_ok=True)
        data = {"question": question, "state": json.loads(state.to_json())}
        self._path(request_id).write_text(json.dumps(data, ensure_ascii=False), encoding="utf-8")
```

1 台なら、これで足ります。2 台に増やすと、質問を受けた台と、承認を受けた台が違うとき、承認待ちの状態が見つからず `404` になります。

| 台数 | 状態の置き方 |
|---|---|
| 1 台 | ファイル（ボリューム）。12 の API のまま |
| 2 台以上 | どの台からも読めるデータベースなどに置く。`StateStore` と同じ `save`・`load`・`delete` を持つクラスを書いて差し替える |

台数を自動で増やすサービスに置くときは、最大の台数を 1 にするか、状態の置き場所を先に替えます。

!!! failure "悪い例"
    質問の API を認証なしでインターネットに開く。台数を自動で増やす設定にしたまま、状態はコンテナの中のファイルに書く。
    試した後、サービスもイメージも消さずに放っておく。

!!! success "良い例"
    入口に認証を置き、最大の台数を決め、状態はボリュームか共有の置き場所に書く。
    予算の通知を先に設定し、手順書に「止め方と消し方」を書いて、試し終わったらその手順で消す。

### 任意（有料）: クラウドのコンテナの実行サービスに置く

!!! warning "任意: 従量課金のクラウドを使います"
    自分の PC やサーバーだけで進める場合は、この節を飛ばしてください（12 の成果物は作れます）。
    試す場合は、先に費用の上限と止め方を決めてください（[学び方](../guide.md) の「従量課金の API は任意」と同じ考え方です）。

LLM は B（クラウドの LLM の API）にする場合の流れです。C（GPU の VM）は、時間あたりの費用が大きいので、ここでは扱いません。

1. **予算と通知を先に設定する**: クラウドの管理画面で、月の予算と、予算に近づいたときの通知を設定する。LLM の API の管理画面でも、利用の上限を設定する
2. **イメージを置く**: 12-2 の CI で作った、コミットの SHA の名前のイメージを、クラウドのレジストリに送る
3. **サービスを作る**: 最小の台数を 0（呼ばれないときは止まる）、最大の台数を 1、CPU とメモリは最小から始める。待ち受けるポートは 8000
4. **秘密を渡す**: 承認の鍵と LLM の API のキーを、シークレットの管理に置き、環境変数で渡す
5. **費用の上限をコードにも置く**: `--price-in`・`--price-out` に公式の料金ページで確かめた単価を、`--max-cost` に 1 回の依頼の上限を渡す（10-4 の `AgentLimits`）。
   クラウドの LLM の API を使うには、その API の会話とツール使用を `ToolChat`（`chat(messages, tools)` を持つクラス）として書く（10-4 の任意の節）
6. **入口を守る**: サービスの認証（呼べる人を絞る設定）を有効にし、誰でも呼べる設定にしない
7. **確かめる**: `/healthz` と、`/ask` を 1 回だけ呼び、記録（12-4）にトークンと費用の見積もりが残ることを確かめる
8. **消す**: 試し終わったら、サービス・レジストリのイメージ・ボリュームやストレージ・作ったキーを消す。翌日、請求の画面で料金が増えていないことを確かめる

!!! note "最小の台数を 0 にしたとき"
    呼ばれない間は止まるので費用を抑えられますが、最初の呼び出しは起動を待つ分だけ遅くなります（コールドスタート）。
    応答時間の監視（12-4）では、この遅れを分けて見ます。

### 配備の手順書を書く

手順書は、自分以外の人が読んでも同じように配備し、止め、消せるように書きます。13 の提出物の `deploy.md` は、この形です。

```markdown
# 配備の手順

## 用意するもの
- Docker と compose が入ったサーバー（メモリ 16 GB 以上。モデル（名前）が載る大きさ）
- リポジトリ直下の .env に AGENT_MODEL と APPROVER_TOKEN（鍵の作り方: python -c "import secrets; print(secrets.token_hex(16))"）

## 手順
1. examples/ で docker compose --env-file ../.env up --build -d
2. docker compose exec ollama ollama pull <モデル名>
3. 確かめ: curl -s localhost:8000/healthz が 200。/ask を 1 回呼び、requests.jsonl に記録が増える

## 戻し方
- 前のコミットに戻して手順 1 をやり直す（イメージはコミットの SHA で区別する）

## 止め方と消し方
- 止める: docker compose down（記録とモデルは残る）
- 消す: docker compose down -v（記録とモデルも消える。記録を残すなら先に写す）

## 監視
- 12-4 の p12_monitor を 1 日 1 回流し、しきい値を超えたら知らせる
```

## 演習

1. 上の手順書の形で、自分の環境（手元の PC か社内のサーバー）に 12 の API を配備する `deploy.md` を書いてください。
   `restart: unless-stopped` を足し、PC を再起動した後も API が立ち上がることを確かめます
2. 12-1 の API を 2 台で動かし、前に負荷を分ける仕組み（ロードバランサー）を置いたとき、承認の流れで何が起きるかを説明してください。
   `StateStore` の代わりに使える置き場所の案と、差し替えるときにテストで確かめることを書きます
3. B の置き方（クラウドの LLM の API）で 1 日 200 件の質問が来るとして、月の費用を見積もってください。1 件あたりのトークン数は、12-4 のサンプルの記録の平均
   （入力 約 2,400・出力 約 100）を使い、単価は使う API の公式の料金ページで確かめた値を使います（07-4 の `cost`）
4. 任意（有料）: 上の「任意（有料）」の手順で、クラウドのコンテナの実行サービスに置き、確かめた後に消してください。かかった費用も書きます

- できたことの確かめ方: 1 は手順書と、再起動の後に `/healthz` が `200` を返した結果。2・3 は説明と計算。4 は手順と費用と、消したことの確かめ
- 目安の時間: 3 時間（4 は別）

解答: [12-3 の解答](answers/12-3.md)

## もし〇〇がなかったら？

**配備の前に決めることの一覧がなかったら**、動いたところで満足して、入口の守りや台数と状態の食い違いに、使われ始めてから気づきます。
承認待ちが消える、知らない人に LLM を使われる、といった問題は、配備の後で直すほど影響が大きくなります。

**止め方と消し方の手順がなかったら**、試しに作ったクラウドのサービスやディスクが残り、使っていないのに請求が続きます。
誰が何のために作ったのかも分からなくなり、消してよいかの判断にも時間がかかります。

## 理解度チェック

1. LLM の置き場所として、手元のサーバーの Ollama・クラウドの LLM の API・GPU つきの VM の費用のかかり方の違いを説明してください。

    ??? note "答え"
        手元の Ollama は API の料金がかからず、電気代とサーバーだけです。クラウドの LLM の API は、使ったトークンに応じた従量課金です。
        GPU つきの VM は、動かしている時間に応じて課金され、使っていない時間もかかります。

2. 12-1 の API を 2 台に増やすと、承認の流れで何が困りますか。

    ??? note "答え"
        承認待ちの状態を、質問を受けた台のファイルに書くので、承認を別の台が受けると状態が見つかりません（`404`）。
        1 台にそろえるか、どの台からも読める置き場所に状態を移します。

3. 設定を環境変数で渡すと、何がうれしいですか。

    ??? note "答え"
        同じイメージを、手元・試験・本番で、設定だけ変えて動かせるからです。秘密もイメージに入れずに、動かすときに渡せます。

4. クラウドで試すとき、作業の最初に予算の通知を設定し、最後に消す手順まで行うのはなぜですか。

    ??? note "答え"
        消し忘れや、誤った設定による呼び出しの暴走に、請求が来る前に気づくためです。
        試し終わったものを消さないと、使っていなくても料金がかかり続けるものがあります。
