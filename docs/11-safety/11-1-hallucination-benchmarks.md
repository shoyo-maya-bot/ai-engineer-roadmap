# 11-1 幻覚とベンチマークの読み方

!!! abstract "到達目標"
    - 幻覚（もっともらしい誤り）の種類を挙げ、RAG の答えから、資料に無い数字を見つけるコードを書ける
    - 評価の点数（公開のベンチマーク・自分の評価セット）を、条件・件数・幅と一緒に読める
    - 同じ評価セットの 2 つの結果の差が、偶然で出る範囲かどうかを確かめられる

## 何か

**幻覚**（ハルシネーション）は、LLM が、事実と違うことや根拠の無いことを、もっともらしく答えることです。
LLM は次のトークンを確率で選ぶ仕組みなので（06-2）、知らないことでも、それらしい文章を作れてしまいます。

| 種類 | 例（08・10 の設計書の Q&A） | 見つけ方 |
|---|---|---|
| 資料と食い違う | 資料は「30 分」なのに「60 分」と答える | 答えの数字や語が、渡した資料にあるかを確かめる |
| 資料に無いことを足す | 資料に無い「土日も使えます」を書き足す | 資料に無い質問を評価セットに入れ、「記載がありません」と答えるかを見る |
| 出典の誤り | 示した出典 [2] に、その内容が書かれていない | 出典の番号が渡した資料の範囲か（08-4）、出典の本文に答えの語があるか |
| 存在しないもの | 無い API・無い関数のオプションを答える | 実物（設計書・公式ドキュメント・コード）と照らす |

**ベンチマーク** は、モデルを比べるために公開されている評価セットと、その点数です。
「このモデルは〇〇のベンチマークで 85 点」のように、モデルの紹介やランキングで使われます。
仕組みは 07-5 の評価セットと同じで、決まった問題を解かせて採点し、平均を出しています。

## なぜ必要か

幻覚は、LLM を業務で使うときのいちばん大きな心配の 1 つです。設計書の値を間違えて答えれば、それを信じた人が誤った実装をします。
幻覚をゼロにはできないので、「見つける仕組み」と「どれくらい起きるかを測る仕組み」を作ります。

点数の読み方を知らないと、次のように判断を誤ります。

- 評価セット 30 件で「正解率が 90.0% から 76.7% に下がった」（09-2 の LoRA）を、確かな悪化だと思い込む（後で見るように、偶然でも起こりうる差です）
- ベンチマークの順位でモデルを選んだが、自分の課題（日本語の問い合わせの分類）では、順位の低いモデルのほうが良かった
- ベンチマークの問題が、モデルの学習データに混ざっていた（**混入**、コンタミネーション）。点が実力より高く出ていた

## どうやるか

### 資料に無い数字を見つける

08 の Q&A では、出典の番号が資料の範囲にあるかを確かめました（08-4）。もう 1 歩進めて、**答えの数字が、渡した資料のどこかにあるか** を確かめます。
設計書の Q&A では、期限・回数・時刻のような数字の間違いが、いちばん困る誤りだからです。

<!-- src: examples/src/roadmap_examples/p11_numbers.py -->
```python title="examples/src/roadmap_examples/p11_numbers.py"
def numbers_in(text: str) -> set[str]:
    """文章の中の数字（全角は半角に、桁区切りのカンマは外す）."""
    text = unicodedata.normalize("NFKC", text)
    return {n.replace(",", "") for n in NUMBER.findall(text)}


def unsupported_numbers(answer: str, contexts: Sequence[str], ignore: Sequence[str] = ()) -> list[str]:
    """答えの数字のうち、資料（contexts）に無いもの. [1] のような出典の番号は数えない. ignore の数字も外す."""
    known = set().union(*(numbers_in(c) for c in contexts)) if contexts else set()
    found = numbers_in(re.sub(r"\[\d+\]", "", answer))
    return sorted(found - known - set(ignore))
```

<!-- src: examples/tests/test_p11_numbers.py -->
```python title="examples/tests/test_p11_numbers.py"
def test_unsupported_numbers() -> None:
    contexts = ["アクセストークンの有効期限は 30 分", "リフレッシュトークンは 7 日"]
    assert unsupported_numbers("有効期限は 60 分です [1]。リフレッシュは 7 日 [2]。", contexts) == ["60"]
    assert unsupported_numbers("上限は１，０００件", ["上限は 1000 件"]) == []
```

- 「60」は資料のどこにも無いので、幻覚の疑いとして返ります。疑いがあれば、答えに注意を添えるか、人の確認に回します
- 数字が資料にあっても、正しい場所の数字とは限りません（「7 日」を有効期限の答えに使うなど）。これは見つけられないので、評価セットの `keywords`（08-4）でも確かめます
- 「三十分」のような漢数字や、計算した結果（「30 分 × 2 = 60 分」）は、この方法では誤りと判定されることがあります。完全な判定ではなく、疑わしい答えを拾う網です

### 答えが無いときに「無い」と言えるかを測る

「資料に無いことを足す」幻覚は、資料に答えが無い質問を評価セットに入れて測ります。
08 の評価セットにも、答えが資料に無い質問があり、「資料に記載がありません」と答えれば正解にしています（08-4）。
答えのある質問だけの評価セットでは、この種類の幻覚は測れません。

### 点数の幅を見る

評価セットの正解率は、「この 30 件では」の値です。同じ種類の問い合わせを別に 30 件集めれば、正解率は少し変わります。
そこで、本当の正解率がありそうな幅（**区間**）を一緒に書きます。ここでは、件数が少ないときにも使いやすいウィルソンの区間を使います。

<!-- src: examples/src/roadmap_examples/p11_numbers.py -->
```python title="examples/src/roadmap_examples/p11_numbers.py"
def wilson_interval(correct: int, total: int, z: float = 1.96) -> tuple[float, float]:
    """正解率の区間（既定は 95%）. 件数が少ないほど、また 0% や 100% に近いほど、素直な計算より当てになる."""
    if total <= 0 or not 0 <= correct <= total:
        raise ValueError("0 <= correct <= total かつ total > 0 にしてください")
    p = correct / total
    denom = 1 + z * z / total
    center = (p + z * z / (2 * total)) / denom
    half = z * math.sqrt(p * (1 - p) / total + z * z / (4 * total * total)) / denom
    return max(0.0, center - half), min(1.0, center + half)
```

```bash
uv run python -m roadmap_examples.p11_numbers --correct 24 --total 30
```

正解率 80% のときの 95% の区間です（`p11_numbers` で計算）。

| 件数 | 正解 | 95% の区間 |
|---|---|---|
| 30 | 24 | 62.7%〜90.5% |
| 100 | 80 | 71.1%〜86.7% |
| 300 | 240 | 75.1%〜84.1% |

30 件では、80% と出ても、本当は 63% ほどかもしれないし、90% ほどかもしれません。
件数を増やすほど幅は狭くなりますが、評価にかかる時間と費用も増えます。13 では、課題に合わせて件数を決めます。

### 2 つの結果の差を確かめる

同じ評価セットで 2 つのやり方を比べるときは、平均の差ではなく、**件ごとに** 比べます（07-5 の `compare`）。
良くなった件と悪くなった件の数が、五分五分でもこれくらい偏るか、を計算するのが **符号検定** です（02-3 の検定の考え方）。

<!-- src: examples/src/roadmap_examples/p11_numbers.py -->
```python title="examples/src/roadmap_examples/p11_numbers.py"
def sign_test(better: int, worse: int) -> float:
    """良くなった件と悪くなった件の数が、偶然（五分五分）でこれ以上偏る確率（両側の符号検定. 02-3）."""
    n = better + worse
    if n == 0:
        return 1.0
    k = min(better, worse)
    tail = sum(math.comb(n, i) for i in range(k + 1)) / 2**n
    return min(1.0, 2 * tail)
```

07 の仮のルールベース分類と、09 の LoRA の結果を比べてみます（どちらも LLM を使わずに流せます）。

```bash
uv run python -m roadmap_examples.p07_classify --mode baseline --out results-baseline.jsonl
```

```text
前: 正解率 66.7%（20 / 30 件）. 95% の区間: 48.8%〜80.8%
後: 正解率 90.0%（27 / 30 件）. 95% の区間: 74.4%〜96.5%
良くなった件 8 / 悪くなった件 1. 偶然でこれ以上偏る確率: 0.039
```

良くなった件が 8、悪くなった件が 1 で、五分五分でこれ以上偏る確率は 0.04 です。偶然だけでは起こりにくい差と言えます。
ただし、09-2 で見たとおり、LoRA の前の「汎用の例だけのモデル」もすでに 90.0% でした。ルールより良くなったのは、LoRA ではなく小さなモデルそのものの効き目です。
何と何を比べた差なのかを、取り違えないようにします。

逆の例もあります。09-2 の、汎用の例だけのモデル（90.0%）と LoRA（r=1・76.7%）の差は、良くなった 1 件・悪くなった 5 件で、確率は 0.22 でした。
13 ポイント下がっても、30 件では「確かに悪くなった」とは言えません。

    1 件の差です。悪くなった件があったかも見ていません。

!!! success "良い例"

### ベンチマークを読む

公開のベンチマークの点数を見るときは、次を確かめます。分からない項目が多いほど、その点数で判断するのは危ういです。

| 確かめること | なぜ |
|---|---|
| 何を測っているか（課題の種類・言語・形式） | 英語の選択問題の点が、日本語の自由記述の点と同じとは限らない |
| 指標の定義（完全一致か・部分点か・人の採点か） | 同じ「正解率」でも、数え方で値が大きく変わる |
| 条件（プロンプト・例示の数・temperature・何回試したうちの何回か） | 条件をそろえないと、モデルを比べられない |
| 件数と幅 | 件数が少ないと、数点の差は偶然の範囲 |
| 混入の恐れ（問題が公開されてから長いか・学習データの説明） | 問題を覚えていれば、実力より高く出る |
| 自分の課題との近さ | 最後に決めるのは、自分の評価セットの結果 |

ベンチマークは「候補を絞る」ために使い、選ぶのは自分の評価セット（07-5）で比べてからにします。06 の成果物の表と同じ考え方です。

## もし〇〇がなかったら？

**幻覚を見つける仕組みがなかったら**、設計書の値を間違えた答えが、出典つきのもっともらしい形で利用者に届きます。
誤りに気づくのは、その値で作ったものが動かなかったときです。

**点数の幅と差の確かめがなかったら**、評価のたびに上がったり下がったりする 1〜2 件の差に振り回されます。
偶然の改善を採用し、偶然の悪化で良い変更を捨てることになります。

## 理解度チェック

1. RAG の答えで、資料に無い数字を見つける確かめは、どんな幻覚を見つけられて、どんな幻覚を見逃しますか。

    ??? note "答え"
        資料と食い違う数字（資料は 30 分なのに 60 分と答える）を見つけられます。
        資料にある数字を間違った場所で使う誤り（有効期限に「7 日」を使う）や、数字を含まない誤りは見逃します。評価セットの語の確かめと組み合わせます。

2. 評価セット 30 件で正解率 80% のとき、95% の区間はおよそどれくらいですか。それは何を意味しますか。

    ??? note "答え"
        およそ 63%〜90% です。同じ種類の問い合わせを別に集めて測れば、この程度の幅で値が変わりうる、という意味です。
        30 件での数ポイントの差は、この幅の中に収まってしまいます。

3. 2 つのやり方を比べるとき、平均の差だけでなく、件ごとに良くなった件と悪くなった件を数えるのはなぜですか。

    ??? note "答え"
        平均が同じでも、良くなった件と悪くなった件が入れ替わっていることがあるからです。
        件ごとに数えれば、差が偶然の範囲か（符号検定）を確かめられ、悪くなった件の原因も調べられます。

4. ベンチマークの「混入」とは何ですか。混入があると、点数はどうなりますか。

    ??? note "答え"
        ベンチマークの問題や答えが、モデルの学習データに混ざっていることです。
        モデルが問題を覚えていれば、解く力より高い点が出ます。09-1 で、学習の例と評価セットを分けたのと同じ問題です。
