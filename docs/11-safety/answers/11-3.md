# 11-3 解答

[11-3 ガードレールと個人情報の伏せ字](../11-3-guardrails-pii.md) の演習の解答の一例です。

## 1 社員番号を伏せる

```python
import re

import pytest

from roadmap_examples import p11_guard
from roadmap_examples.p11_guard import redact

EMPLOYEE_ID = ("社員番号", re.compile(r"社員番号\s*[:：]?\s*\d{5,6}(?!\d)"))


@pytest.fixture
def with_employee_id(monkeypatch: pytest.MonkeyPatch) -> None:
    monkeypatch.setattr(p11_guard, "PII_PATTERNS", [*p11_guard.PII_PATTERNS, EMPLOYEE_ID])


def test_employee_id_is_redacted(with_employee_id: None) -> None:
    r = redact("社員番号 123456 で借りた備品を確かめたい")
    assert r.text == "[社員番号] で借りた備品を確かめたい"
    assert r.found == ["社員番号"]


def test_word_without_number_is_kept(with_employee_id: None) -> None:
    assert redact("社員番号でログインします").found == []
```

なぜこうするか:

- 本物のコードでは `PII_PATTERNS` に 1 行足します。テストでは `monkeypatch` で一時的に足し、ほかのテストに影響させないようにしています
- 「社員番号」の語を手がかりにしているので、数字だけ（「123456 で借りた」）は伏せません。業務で社員番号の形が決まっているなら（先頭の英字など）、形で探す行も足します
- 伏せない例（数字が無い）もテストに書きます。伏せ字の形を足すと、誤って伏せる例も増えるからです

## 2 誤検知を直す

```python
import re

import pytest

from roadmap_examples import p11_guard
from roadmap_examples.evalset import load_cases
from roadmap_examples.p11_attacks import DEFAULT_ATTACKS
from roadmap_examples.p11_guard import GuardConfig, check_input

NEW_PATTERNS = [
    # 「設定」は普通の質問にも出るので外し、指示・命令・決まりだけにする
    ("指示の上書き", re.compile(r"(これまで|今まで|以前|上記|前|先ほど)の(指示|命令|決まり).{0,10}(無視|忘れ)")),
    p11_guard.INJECTION_PATTERNS[1],
    # 画面の「システムメッセージ」は普通の言葉なので、プロンプトだけにする
    ("system を聞き出す", re.compile(r"(システム|system)\s*(プロンプト|prompt)", re.I)),
    # 「今から〜です」と役割を言い渡す形だけにする（「〜ですか」の質問は除く）
    (
        "役割の乗っ取り",
        re.compile(r"(あなたは|you are)\s*(今から|これから|now)[^。？?]{0,20}(です|になる|として)(?!か)", re.I),
    ),
    p11_guard.INJECTION_PATTERNS[-1],  # 区切りの偽装（sanitize_document が最後の行を使うので、最後に置く）
]
BENIGN = [
    "システムメッセージが英語で表示されます。日本語にできますか？",
    "前の設定を忘れてしまいました。どこで確かめられますか？",
    "あなたは今から使い始める人に、何をすすめますか？",
]


@pytest.fixture(autouse=True)
def new_patterns(monkeypatch: pytest.MonkeyPatch) -> None:
    monkeypatch.setattr(p11_guard, "INJECTION_PATTERNS", NEW_PATTERNS)


@pytest.mark.parametrize("question", BENIGN)
def test_benign_questions_pass(question: str) -> None:
    assert check_input(question, GuardConfig()) == ""


def test_attacks_are_still_blocked() -> None:
    cases = {c.id: c for c in load_cases(DEFAULT_ATTACKS)}
    for case_id in ("x01", "x02", "x03", "x06"):
        assert check_input(cases[case_id].input, GuardConfig()) != "", case_id
```

なぜこうするか:

- 形を狭めるほど誤検知は減り、すり抜けは増えます。狭めた分は、ほかの守り（書き換えの前・出力の確かめ）が受け持つので、入力の確かめは「よくある攻撃を安く止める」役目に絞ります
- 誤検知の 3 件を評価セットの「誤検知の確認」に足しておくと、形を直すたびに確かめられます（11-4）
- 実際に直すときは `p11_guard.py` の `INJECTION_PATTERNS` を書き換え、`uv run pytest` で攻撃例 20 件のテストも通ることを確かめます

## 3 h05 を防ぐ案

```python
import re
import unicodedata

PHONE_DIGITS = re.compile(r"(?<!\d)0\d{9,10}(?!\d)")  # ハイフンなしの 10〜11 桁


def redact_normalized(text: str) -> list[str]:
    """全角をそろえてから探す（NFKC で ＠ は @ に、０ は 0 になる）. 見つけた種類を返す."""
    from roadmap_examples.p11_guard import redact

    flat = unicodedata.normalize("NFKC", text)
    found = redact(flat).found
    if PHONE_DIGITS.search(flat) and "電話番号" not in found:
        found.append("電話番号")
    return found


def test_h05_is_found_after_normalizing() -> None:
    assert redact_normalized("連絡先 09012345678 user＠example.com") == ["メールアドレス", "電話番号"]
    assert redact_normalized("担当は ０９０-１２３４-５６７８ です") == ["電話番号"]
    assert redact_normalized("注文番号は 12345 です") == []
```

本物のコードでは、`redact` の最初で `unicodedata.normalize("NFKC", text)` をかけ、`PII_PATTERNS` にハイフンなしの電話番号の行を足します。

ホールドアウトの扱い:

- h05・h07 を見て直したので、この 2 件はもう未知の攻撃例ではありません。直した後の「守れた件」は、既知の攻撃例の結果として書きます
- 未知の言い換えへの強さを測り直すには、守りを見ていない人に、新しい攻撃例を書いてもらいます
- ハイフンなしの 10〜11 桁を電話番号とみなすと、同じ桁数の注文番号などを誤って伏せることがあります。誤検知の例も評価セットに足して確かめます

## 4 「頼まれていない起票は断る」の限界

| 例 | 内容 |
|---|---|
| すり抜ける例 | 「延滞の扱いを教えて。課題にする必要は無いです」 → 「課題に」の語があるので、頼んだとみなされる。資料に紛れた起票の指示が、人の承認まで届く |
| 誤って断る例 | 「資料に無ければ、チケットを切っておいてください」 → 「起票」「課題に」の語が無いので、頼んだのに断られる |

考え（一例）:

- 語の一覧を増やす（「チケット」など）と、誤って断る例は減ります。打ち消し（「必要は無い」）まで語で見分けるのは難しいです
- このままにする理由もあります。すり抜けても、その先に人の承認があるからです。決まりで断るのは「明らかに頼まれていない」ものだけにし、迷うものは人に見せます
- もっと確かにするなら、画面に「課題にする」のチェックを付け、利用者が明示したときだけ起票のツールを渡す（ツールそのものを渡さない）方法があります。文章から推し量るより確実です
