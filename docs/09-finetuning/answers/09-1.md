## 1 外れた 10 件を分ける

仮のルールベース分類で外れた 10 件です（`--out` の結果で、`score` が 0 の件）。

| id | 問い合わせ（要約） | 正解 → 予測 | 外れ方 | 直し方 |
|---|---|---|---|---|
| c005 | 解約した月の分まで引き落とされた | billing → contract | 判断の癖（請求と契約にまたがる） | 例示 → 学習 |
| c006 | 請求額の画面でエラー。返金はいつか | billing → bug | 判断の癖（最終的に何をしてほしいか） | 例示 → 学習 |
| c011 | 確認コードが受け取れず入れない | account → other | 言い換え（「ログイン」と書いていない） | 例示 → 学習 |
| c014 | 検索ボタンを押しても何も起きない | bug → other | 言い換え | 例示 → 学習 |
| c015 | CSV が文字化けする | bug → other | 言い換え | 例示 → 学習 |
| c016 | メモが一覧に表示されません | bug → other | 言い換え（「表示されない」と活用が違う） | 例示 → 学習 |
| c018 | プラン変更の画面で固まる | bug → contract | 判断の癖 | 例示 → 学習 |
| c022 | 利用人数を増やしたい | contract → other | 言い換え | 例示 → 学習 |
| c023 | 支払いの負担が大きいので安いプランを検討 | contract → billing | 判断の癖 | 例示 → 学習 |
| c024 | お試しの後に自動で有料になるか | contract → other | 言い換え | 例示 → 学習 |

なぜこう分けるか:

- どの件も、答えに要る知識（資料）は問い合わせ文の中にあります。知らないことを聞かれた件は無いので、RAG では直りません
- 「判断の癖」は、2 つの分類にまたがるときに、どちらを選ぶかの決まりです。07 の手順の 3（「困っている原因に近いほう」）を例示で示し、
  それでも外れる分を学習で直します
- 「言い換え」は、ルールの語の一覧に無い書き方です。LLM なら言い換えに強いので、まず 07 のプロンプトで流して、残った外れを見ます
- 分け方は 1 つではありません。件ごとに、なぜその直し方を選んだかを書けていれば構いません

## 2 句読点の違いも同じとみなす

```python
import re
import unicodedata
from collections.abc import Sequence

from roadmap_examples.evalset import EvalCase, load_cases
from roadmap_examples.p07_classify import DEFAULT_EVAL
from roadmap_examples.p09_lora import SFT_TRAIN

# 全角は NFKC で半角になるので、半角の記号と空白を消せばよい
PUNCT = re.compile(r"[、。,.!?「」『』()・\s]")


def loose(text: str) -> str:
    return PUNCT.sub("", unicodedata.normalize("NFKC", text))


def near_overlaps(train: Sequence[EvalCase], evaluation: Sequence[EvalCase]) -> list[tuple[str, str]]:
    seen = {loose(c.input): c.id for c in evaluation}
    return [(c.id, seen[loose(c.input)]) for c in train if loose(c.input) in seen]


def test_punctuation_differences_are_overlaps() -> None:
    train = [EvalCase("t1", "CSV を出力すると、文字化けします！", {})]
    assert near_overlaps(train, load_cases(DEFAULT_EVAL)) == [("t1", "c015")]


def test_training_set_has_no_near_overlaps() -> None:
    assert near_overlaps(load_cases(SFT_TRAIN), load_cases(DEFAULT_EVAL)) == []
```

なぜこうするか:

- NFKC で全角の「！」「？」「，」は半角になるので、消す記号は半角だけを並べれば足ります
- 本物の学習の例でも重なりが無いことを、同じテストで確かめています。例を足すたびに流せます
- 句読点より大きな違い（語順の入れ替え・言い換え）は、この方法では見つかりません。
  気になる場合は、08 のエンベディングで似た文章を探し、似すぎた組を人が見て決める方法もあります

## 3 4 つの要望

| 要望 | 先に試すこと | 理由 |
|---|---|---|
| API のエラーコードの意味に答えてほしい | RAG | 設計書にある知識。設計書が変わっても差し替えるだけで済み、出典も示せる |
| 分類を小さなモデルで同じ正解率にしたい | プロンプト → ファインチューニング | 小さなモデルで例示を試し、足りなければ学習。分類の決まりは変わりにくく、例も集めやすい |
| いつも「結論 → 理由 → 出典」の順に書いてほしい | プロンプト（必要なら構造化出力） | 形の問題。手順と例示で直ることが多い。直らなければ、学習で形をそろえる |
| 毎週変わる当番表に答えてほしい | RAG | 毎週変わる知識。学習すると毎週学習し直しになる |

考察で見ること:

- 「小さなモデルで同じ正解率」は、学習が効きやすい代表です。ただし、まず小さなモデルにプロンプトだけで流し、差を測ってから決めます
- 組み合わせる答え（RAG で資料を渡し、形は学習でそろえる）でも構いません。理由が書けていればよい答えです
