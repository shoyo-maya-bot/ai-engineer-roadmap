# 09-3 量子化と GPU のメモリ

!!! abstract "到達目標"
    - 量子化（重みを少ないビット数で持つこと）の仕組みと、塊ごとに倍率を持つ理由を、コードで説明できる
    - 量子化で小さくなる分と、答えがずれる分を、評価セットで測れる
    - 学習（フルの調整・LoRA・QLoRA）と推論（重み・KV キャッシュ）に要るメモリを見積もり、手元で動くかを判断できる

## 何か

**量子化** は、重み 1 つを少ないビット数の整数で持ち、「整数 × 倍率（scale）」で元の値に近い値を表す方法です。
06-4 では、量子化でモデルのファイルが小さくなることを見ました。09-3 では、その中身と、学習のときのメモリを扱います。

いちばん素直な量子化は、次の形です（対称な量子化）。

```text
4 ビットなら、使える整数は -7〜7（qmax = 7）
倍率 scale = いちばん大きい絶対値 ÷ qmax
整数 q = 四捨五入(重み ÷ scale)        → 保存するのは q と scale
戻した値 = q × scale                    → 元の重みとの差が「量子化のずれ」
```

行列全体で 1 つの倍率にすると、1 つだけ大きな値（外れ値）があったとき、倍率が大きくなり、ほかの小さな値がみな 0 に丸められてしまいます。
そこで、重みを小さな **塊（グループ・ブロック）** に分け、塊ごとに倍率を持ちます。外れ値の影響は、その塊の中だけで済みます。

GPU のメモリ（VRAM）は、ふつうのメモリより少ないことが多く、「モデルが GPU に載るか」で速さが大きく変わります（06-4 の `ollama ps`）。
学習では、重みのほかに、勾配や最適化の状態も載せるので、推論よりずっと多くのメモリが要ります。

## なぜ必要か

- 「8B のモデルを LoRA で学習したい」と思っても、要るメモリを見積もらずに始めると、途中でメモリが足りずに止まります。クラウドの GPU なら、止まるまでの時間も費用になります
- 量子化すると小さく速くなりますが、答えがずれることがあります。「何ビットまで下げてよいか」は、評価セットで測って決めます
- 長いコンテキストを使うと、重みとは別に KV キャッシュ（後で説明）が増えます。重みだけで見積もると、長い文書を入れたときに足りなくなります

## どうやるか

### 量子化を書く

<!-- src: examples/src/roadmap_examples/p09_quant.py -->
```python title="examples/src/roadmap_examples/p09_quant.py"
def quantize(w: np.ndarray, bits: int = 8, group_size: int | None = None) -> Quantized:
    """対称な量子化. group_size が None なら行列全体で 1 つの倍率、渡すと塊ごとに倍率を持つ."""
    if not 2 <= bits <= 8:
        raise ValueError("bits は 2〜8 にしてください")
    qmax = 2 ** (bits - 1) - 1
    flat = w.reshape(-1)
    if group_size is None:
        groups = flat[None, :]
    else:
        if flat.size % group_size:
            raise ValueError(f"重みの数（{flat.size}）が group_size（{group_size}）で割り切れません")
        groups = flat.reshape(-1, group_size)
    absmax = np.abs(groups).max(axis=1, keepdims=True)
    scale = np.where(absmax > 0, absmax / qmax, 1.0)
    q = np.clip(np.round(groups / scale), -qmax, qmax).astype(np.int8)
    return Quantized(q, scale, w.shape, bits, group_size)


def dequantize(qz: Quantized) -> np.ndarray:
    return (qz.q * qz.scale).reshape(qz.shape)
```

- 整数は `int8` の配列に入れています（4 ビットでも 1 つ 1 バイト）。大きさの計算（`n_bytes`）では、ビット数どおりに詰めたとして数えます
- 倍率も保存が要ります。塊を小さくするほど倍率の数が増え、その分だけ大きくなります

外れ値があるとき、塊ごとの倍率が効くことは、テストで確かめています。

    w = np.random.default_rng(0).normal(0, 0.02, (32, 512))
    w[0, 0] = 1.0  # 1 つだけ大きな値（外れ値）

```

```

実際の量子化の形式（llama.cpp の `Q4_K_M` など）は、塊の分け方や倍率の持ち方をもっと工夫しています。
名前ごとの 1 つあたりのビット数は、06-4 で見た llama.cpp の量子化ツールの説明にあります。

### ずれを評価セットで測る

09-2 で LoRA を足し込んだ小さなモデルの重みを量子化し、07 の評価セットの正解率がどう変わるかを測ります。

```bash
uv run python -m roadmap_examples.p09_quant
```

手元で流した結果です（09-2 と同じ条件）。

| 重みの持ち方 | w1 の大きさ（バイト） | w1 の平均のずれ | 正解率 |
|---|---|---|---|
| 64 ビット（元のまま） | 131,072 | 0.0000 | 90.0% |
| 8 ビット | 16,386 | 0.0033 | 90.0% |
| 4 ビット・32 個ずつの塊 | 9,216 | 0.0331 | 90.0% |
| 4 ビット・全体で 1 つの倍率 | 8,194 | 0.0600 | 90.0% |
| 2 ビット・32 個ずつの塊 | 5,120 | 0.2200 | 76.7% |
| 2 ビット・全体で 1 つの倍率 | 4,098 | 0.3037 | 56.7% |

- 4 ビットまでは、ずれはあっても正解率は変わりませんでした。大きさは 64 ビットの 7% ほどです
- 2 ビットにすると答えが崩れ始めます。塊ごとの倍率なら 76.7% で止まりましたが、全体で 1 つの倍率では 56.7% まで下がりました
- この表は小さなモデルでの結果です。LLM では、量子化で落ちやすい仕事（計算・長い指示を守るなど）とそうでない仕事があります。
  自分の評価セットで、量子化の前後を比べてから決めます（例: 同じモデルの `Q8_0` と `Q4_K_M` を 07 の評価で比べる）

!!! failure "悪い例"
    「4 ビットでも精度はほとんど落ちないと聞いたので、いちばん小さい量子化を選ぶ」。
    自分の評価セットで測らずに、一般論で決めている。

!!! success "良い例"
    同じモデルの 8 ビットと 4 ビットを、07 の評価セットで流して比べる。差が評価セットのぶれ（11-1）の中なら、小さく速いほうを選ぶ。
    差が大きいタグ（例: 紛らわしい）があれば、そのタグを使う仕事では大きいほうを使う。

### 学習のメモリを見積もる

学習では、1 つの重みあたり、次のメモリが要ります。16 ビットと 32 ビットを混ぜる学習（混合精度）と、最適化の方法 AdamW の場合です
（[公式ドキュメント: 学習のメモリの内訳](https://huggingface.co/docs/transformers/model_memory_anatomy)）。

| 中身 | 1 つあたり |
|---|---|
| 重み（16 ビットの写しと、32 ビットの元） | 6 バイト |
| 最適化の状態（AdamW の 2 つの値。32 ビット） | 8 バイト |
| 勾配（32 ビット） | 4 バイト |
| 合計 | **18 バイト** |

これに、途中の計算の値（活性化）が加わります。活性化は、バッチの大きさと入力の長さで大きく変わるので、ここでは数えません。

LoRA では、18 バイトかかるのは学習する小さな行列だけです。固定した元の重みは、16 ビットなら 2 バイト、QLoRA で 4 ビットなら 0.5 バイトです。

<!-- src: examples/src/roadmap_examples/p09_quant.py -->
```python title="examples/src/roadmap_examples/p09_quant.py"
def training_gb(params_billion: float, method: str, trainable: int = 0) -> float:
    """学習に要るメモリの目安（GB. 活性化を除く）. trainable は LoRA で学習する重みの数.

    full:  全部の重みを学習する（1 つあたり 18 バイト）
    lora:  元の重みは 16 ビットで固定（2 バイト）+ LoRA の重みだけ 18 バイト
    qlora: 元の重みは 4 ビットで固定（0.5 バイト）+ LoRA の重みだけ 18 バイト
    """
    frozen_bits = {"full": None, "lora": 16, "qlora": 4}
    if method not in frozen_bits:
        raise ValueError(f"method は {', '.join(frozen_bits)} のどれかにしてください")
    if method == "full":
        return params_billion * TRAIN_BYTES_PER_PARAM
    return weights_gb(params_billion, frozen_bits[method]) + trainable * TRAIN_BYTES_PER_PARAM / 1e9
```

`weights_gb` は 06-4 の「パラメータの数 × ビット数 ÷ 8」です。架空の 8B のモデル（32 層・隠れ層 4096）に、
各層の 4 つの行列へ r=16 の LoRA を付けたとして見積もると、次のようになります（`p09_quant` の既定の値）。

```text
LoRA で学習する重み: 16,777,216 個（全体の 0.21%）
| やり方 | 学習のメモリの目安（GB. 活性化を除く） |
|---|---|
| フルの調整 | 144.0 |
| LoRA | 16.3 |
| QLoRA | 4.3 |
| （参考）推論の重みだけ・4 ビット | 4.0 |
```

フルの調整は、1 枚の GPU には載らない大きさです。QLoRA なら、活性化の分を足しても、メモリの多い GPU 1 枚に収まる見込みが立ちます。
自分のモデルの層の数や隠れ層の大きさは、モデルの設定（Ollama なら `/api/show` の `model_info`。06-4）で確かめて、`--layers` などに渡します。

### 推論のメモリ: KV キャッシュ

LLM は、答えを 1 トークンずつ作ります。そのたびに前のトークンの計算をやり直さないよう、
アテンション（05-3）のキー（K）とバリュー（V）を、層ごと・トークンごとに取っておきます。これを **KV キャッシュ** と呼びます
（[公式ドキュメント: KV キャッシュ](https://huggingface.co/docs/transformers/cache_explanation)）。

<!-- src: examples/src/roadmap_examples/p09_quant.py -->
```python title="examples/src/roadmap_examples/p09_quant.py"
def kv_cache_gb(layers: int, kv_heads: int, head_dim: int, context: int, bits: int = 16, batch: int = 1) -> float:
    """推論の KV キャッシュの目安（GB）. 層ごと・トークンごとに、キー（K）とバリュー（V）を 1 組ずつ持つ."""
    return 2 * layers * kv_heads * head_dim * context * batch * bits / 8 / 1e9
```

架空のモデル（32 層・キーとバリューのヘッド 8 個・1 ヘッド 128 次元・16 ビット）で計算すると、
コンテキスト 8,192 トークンで約 1.1 GB、32,768 トークンで約 4.3 GB です。コンテキストの長さに比例して増えます。
06-2 で「使うコンテキストの長さは設定で決まる」と見たのは、このメモリを使うかどうかを決めているからです。

推論に要るメモリの見積もりは、次の合計です。

```text
重み（weights_gb）+ KV キャッシュ（kv_cache_gb）+ 実行に使う分（余裕を持たせる）
```

動かした後は、06-4 と同じく `ollama ps` で、GPU に載ったかを確かめます。

### 手元で動くかを判断する

| やりたいこと | 見積もるもの | 手元で無理なら |
|---|---|---|
| 推論（07・08・10 で使う） | 重み + KV キャッシュ | 小さいモデル・強い量子化・短いコンテキストにする |
| LoRA の学習 | 固定した重み + 学習する重み × 18 バイト + 活性化 | QLoRA にする・r を下げる・入力を短くする・バッチを小さくする |
| フルの調整 | 全部の重み × 18 バイト + 活性化 | ほとんどの場合、LoRA に切り替える |

見積もりは目安です。最初は小さな設定で動かし、実際のメモリの使い方を見てから広げます。

## 演習

1. `quantize` で 3 ビットの量子化を、塊ごと（32 個）と全体で 1 つの倍率の両方で試し、`p09_quant` の表に 2 行足したときの正解率を調べてください。
   さらに、「3 ビットにすると、平均のずれは 4 ビットより大きくなる」ことをテストで確かめます
2. `group_size` を 8・32・128 と変えたとき、4 ビットの `w1` の大きさ（`n_bytes`）と平均のずれがどう変わるかを表にし、塊の大きさの決め方を説明してください
3. `p09_quant --params 1 --layers 16 --hidden 2048 --rank 8` を流し、架空の 1B のモデルを手元の PC で LoRA の学習ができそうかを、PC のメモリと比べて判断してください。
   KV キャッシュ（コンテキスト 4,096 トークン・ヘッド 8・128 次元・16 層と仮定）も足して、推論に要るメモリも見積もります

- 目安の時間: 3 時間

## もし〇〇がなかったら？

**量子化がなかったら**、8B のモデルは 16 ビットで約 16 GB の重みが要り、多くの個人の PC では動きません（06-4）。
ローカルのモデルを基本にするこの教材のやり方は、量子化があって初めて成り立っています。

**メモリの見積もりがなかったら**、学習を始めてから足りないと分かり、設定を変えては流し直すことになります。
クラウドの GPU なら、その試行錯誤の時間がすべて費用になります。先に見積もり、収まる設定を選んでから始めます。

## 理解度チェック

1. 行列全体で 1 つの倍率にする量子化で、外れ値が 1 つあると何が起きますか。塊ごとに倍率を持つと、なぜ防げますか。

    ??? note "答え"
        倍率が外れ値に合わせて大きくなり、ほかの小さな値がみな同じ整数（0 の近く）に丸められて、ずれが大きくなります。
        塊ごとに倍率を持てば、外れ値の影響はその塊の中だけで済み、ほかの塊は小さな倍率で細かく表せます。

2. 混合精度と AdamW の学習で、重み 1 つあたり約 18 バイト要るのはなぜですか。内訳を答えてください。

    ??? note "答え"
        重み 6 バイト（16 ビットの写し 2 + 32 ビットの元 4）、最適化の状態 8 バイト（AdamW の 2 つの値を 32 ビットで）、勾配 4 バイト（32 ビット）の合計です。
        これに活性化が加わります。

3. LoRA と QLoRA で、学習のメモリが大きく減るのはなぜですか。

    ??? note "答え"
        18 バイトかかるのは、学習する小さな行列だけになるからです。固定した元の重みは、LoRA なら 16 ビット（2 バイト）、
        QLoRA なら 4 ビット（0.5 バイト）で持つだけで済みます。

4. KV キャッシュとは何ですか。コンテキストを 4 倍に長くすると、KV キャッシュのメモリはどうなりますか。

    ??? note "答え"
        答えを 1 トークンずつ作るときに、前のトークンのキーとバリューを層ごとに取っておくものです。
        トークンの数に比例するので、コンテキストを 4 倍にすると、KV キャッシュのメモリも約 4 倍になります。
