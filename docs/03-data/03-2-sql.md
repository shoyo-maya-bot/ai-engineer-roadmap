# 03-2 SQL での集計と結合

!!! abstract "到達目標"
    - SELECT・WHERE・GROUP BY・HAVING・JOIN で集計と結合を書き、pandas の同じ処理と対応づけられる
    - 内部結合と左外部結合の違いを、行が消える・増える場面で説明できる
    - NULL を含む集計（COUNT・AVG）の結果を正しく読み、値はプレースホルダーで渡せる

## 何か

業務のデータの多くは、データベースの表に入っています。**SQL** は、表からデータを取り出し、集計し、つなぐための言語です。
この章では、Python の標準ライブラリで使える **SQLite**（ファイルやメモリの中に作るデータベース）を使います
（[公式ドキュメント: sqlite3](https://docs.python.org/3/library/sqlite3.html)）。サーバーは要りません。

同じ処理は pandas でも書けます。2 つを対応づけて覚えます
（[pandas: SQL との比較](https://pandas.pydata.org/docs/getting_started/comparison/comparison_with_sql.html)）。

| やりたいこと | SQL | pandas |
|---|---|---|
| 列を選ぶ | `SELECT id, category` | `df[["id", "category"]]` |
| 行を絞る（集計の前） | `WHERE channel = 'email'` | `df[df["channel"] == "email"]` |
| まとめて数える | `GROUP BY channel` と `COUNT(*)` | `df.groupby("channel").size()` |
| 集計の結果で絞る | `HAVING COUNT(*) >= 10` | 集計した表を `[...]` で絞る |
| 表をつなぐ | `LEFT JOIN customers ON ...` | `df.merge(customers, on=..., how="left")` |
| 並べる | `ORDER BY n DESC` | `sort_values("n", ascending=False)` |

SQL の文の中では、書く順（SELECT → FROM → WHERE → GROUP BY → HAVING）と、処理される順（FROM → WHERE → GROUP BY → HAVING → SELECT）が違います。
WHERE は集計の前、HAVING は集計の後に行を絞ります。

## なぜ必要か

- 100 万件の問い合わせを全部 Python に読み込んでから数えるより、データベースで集計してから結果だけを受け取るほうが、速く、メモリも使わない
- 表の結合を誤ると、行が黙って消えたり、増えたりする。学習データの件数が知らないうちに変わる
- NULL（値が無い）の扱いを知らないと、平均や件数を読み違える

この章では、03-1 で読んだ汚れた CSV と、整えた後の表の両方を SQLite に入れて、違いを確かめます。

## どうやるか

### DataFrame を SQLite に入れる

<!-- src: examples/src/roadmap_examples/p03_sql.py -->
```python title="examples/src/roadmap_examples/p03_sql.py"
def connect(tables: Mapping[str, pd.DataFrame]) -> sqlite3.Connection:
    """メモリの中の SQLite に、DataFrame を表として入れる（表の名前 → DataFrame）."""
    conn = sqlite3.connect(":memory:")
    for name, df in tables.items():
        df.to_sql(name, conn, index=False)
    return conn


def query(conn: sqlite3.Connection, sql: str, params: Mapping[str, object] | None = None) -> pd.DataFrame:
    return pd.read_sql_query(sql, conn, params=params)
```

`":memory:"` は、メモリの中だけのデータベースです。接続を閉じると消えるので、試すのに向いています。
SQL の結果は `pd.read_sql_query` で DataFrame として受け取ります。

### GROUP BY で数える: 表記ゆれが見える

整える前の表で、窓口ごとの件数を数えます。

<!-- src: examples/src/roadmap_examples/p03_sql.py -->
```python title="examples/src/roadmap_examples/p03_sql.py"
CHANNEL_COUNTS = """
SELECT channel, COUNT(*) AS n
FROM inquiries
GROUP BY channel
ORDER BY n DESC, channel
"""
```

結果は 14 行に分かれます。「メール」「mail」「E-mail」「ﾒｰﾙ」は、データベースから見れば別の値です。
集計の前に、値をそろえる必要があります（03-3）。

<!-- src: examples/tests/test_p03_sql.py -->
```python title="examples/tests/test_p03_sql.py"
def test_raw_channel_counts_show_spelling_variants(raw_conn) -> None:
    raw, conn = raw_conn
    sql = query(conn, CHANNEL_COUNTS)
    pd.testing.assert_frame_equal(sql, channel_counts(raw), check_dtype=False)
    email_like = {"メール", "mail", "E-mail", "ﾒｰﾙ"}
    assert email_like <= set(sql["channel"])  # 同じ「メール」が 4 つの行に分かれる
    assert len(sql) == 14
```

`pd.testing.assert_frame_equal` で、SQL の結果と pandas の版（`channel_counts`）が同じ表になることも確かめています。

### JOIN: 内部結合は行を黙って消す

問い合わせの表に、顧客の表からプランをつなぎます。結合の種類で、残る行の数が変わります。

<!-- src: examples/src/roadmap_examples/p03_sql.py -->
```python title="examples/src/roadmap_examples/p03_sql.py"
JOIN_ROW_COUNTS = """
SELECT
  (SELECT COUNT(*) FROM inquiries) AS inquiries,
  (SELECT COUNT(*) FROM inquiries AS i JOIN customers AS c ON i.customer_id = c.customer_id) AS inner_join,
  (SELECT COUNT(*) FROM inquiries AS i LEFT JOIN customers AS c ON i.customer_id = c.customer_id) AS left_join
"""
```

| 結合 | 残る行 | 整える前の表での行の数 |
|---|---|---|
| 内部結合（`JOIN`） | 両方の表に相手がいる行だけ | 147 件中 126 件 |
| 左外部結合（`LEFT JOIN`） | 左の表の行はすべて。相手がいなければ右の列は NULL | 147 件 |

内部結合で消えた 21 件は、`K0019`・`k-0021` のように顧客 ID の書き方が違う 19 件と、顧客の一覧に無い ID（`K-0099` など）の 2 件です。
エラーは出ず、件数が減るだけです。

!!! failure "悪い例"
    内部結合で学習データを作る。顧客 ID の書き方が違う問い合わせが、知らないうちに学習から消える。

!!! success "良い例"
    左外部結合でつなぎ、相手がいなかった行の数を数えて報告する。結合の前に、キーの書き方をそろえる。

逆に、右の表に同じキーの行が 2 つあると、左の 1 行が 2 行に **増えます**。
pandas の `merge` では `validate="many_to_one"` を付けると、右の表のキーが重複しているときにエラーにできます
（[公式ドキュメント: merge](https://pandas.pydata.org/docs/reference/api/pandas.merge.html)）。03 の成果物のパイプラインでも使っています。

### 集計と NULL: COUNT(*) と COUNT(列) は違う

整えた後の表で、窓口ごとの件数と、平均の対応時間を求めます。

<!-- src: examples/src/roadmap_examples/p03_sql.py -->
```python title="examples/src/roadmap_examples/p03_sql.py"
MINUTES_BY_CHANNEL = """
SELECT channel,
       COUNT(*) AS n,
       COUNT(response_minutes) AS n_known,
       AVG(response_minutes) AS avg_minutes
FROM inquiries
GROUP BY channel
HAVING COUNT(*) >= :min_rows
ORDER BY avg_minutes DESC, channel
"""
```

`COUNT(*)` は行の数、`COUNT(列)` は NULL でない値の数です。`AVG(列)` も NULL を除いて平均します
（[SQLite: 集計関数](https://www.sqlite.org/lang_aggfunc.html)）。

| channel | n（行の数） | n_known（対応時間がある） | avg_minutes |
|---|---|---|---|
| phone | 16 | 16 | 40.4 |
| email | 61 | 56 | 38.0 |
| chat | 30 | 28 | 37.7 |
| form | 16 | 15 | 34.5 |

email の平均は、61 件ではなく、対応時間が分かっている 56 件だけで計算しています。
平均を報告するときは、何件から計算したか（`n_known`）も一緒に書きます。

窓口が分からない unknown は 7 件しかないので、`HAVING COUNT(*) >= 10` で外しました。件数の少ないグループの平均はぶれやすいからです。

pandas の版でも、`count()` と `mean()` は欠損を除きます。2 つの結果が同じことをテストで確かめています。

<!-- src: examples/src/roadmap_examples/p03_sql.py -->
```python title="examples/src/roadmap_examples/p03_sql.py"
def minutes_by_channel(df: pd.DataFrame, min_rows: int) -> pd.DataFrame:
    """MINUTES_BY_CHANNEL の pandas 版. count() と mean() も欠損を数えない."""
    out = (
        df.groupby("channel")
        .agg(
            n=("id", "size"),
            n_known=("response_minutes", "count"),
            avg_minutes=("response_minutes", "mean"),
        )
        .reset_index()
    )
    out = out[out["n"] >= min_rows]  # HAVING に当たる
    return out.sort_values(["avg_minutes", "channel"], ascending=[False, True], ignore_index=True)
```

### 値はプレースホルダーで渡す

SQL の文に値を埋め込むときは、文字列をつなげず、プレースホルダー（`:customer_id` や `?`）で渡します。

<!-- src: examples/src/roadmap_examples/p03_sql.py -->
```python title="examples/src/roadmap_examples/p03_sql.py"
INQUIRIES_OF_CUSTOMER = """
SELECT id, category, input
FROM inquiries
WHERE customer_id = :customer_id
ORDER BY id
"""
```

!!! failure "悪い例"
    ```python
    sql = f"SELECT * FROM inquiries WHERE customer_id = '{customer_id}'"  # 入力が SQL の一部になる
    ```

!!! success "良い例"
    ```python
    rows = query(conn, INQUIRIES_OF_CUSTOMER, {"customer_id": customer_id})  # 入力はいつも「値」
    ```

文字列をつなげると、`x' OR '1'='1` のような入力で条件を書き換えられます（SQL インジェクション）。
プレースホルダーなら、入力は SQL の一部にならず、ただの値として比べられます。テストで確かめています。

<!-- src: examples/tests/test_p03_sql.py -->
```python title="examples/tests/test_p03_sql.py"
def test_placeholder_treats_input_as_a_value(clean) -> None:
    conn = connect({"inquiries": clean})
    assert len(query(conn, INQUIRIES_OF_CUSTOMER, {"customer_id": "K-0031"})) == 5
    # 文字列をつなげて SQL を作ると条件を書き換えられる入力も、プレースホルダーならただの値
    assert query(conn, INQUIRIES_OF_CUSTOMER, {"customer_id": "x' OR '1'='1"}).empty
```

## もし〇〇がなかったら？

**結合の種類を意識していなかったら**、内部結合で問い合わせの 1 割以上が消えたまま、学習データを作ります。
消えたのは「顧客 ID の書き方が違う」件、つまり特定の窓口や期間の件かもしれず、モデルがその件を学べません。
件数を数えていなければ、消えたこと自体に気づきません。

**NULL の扱いを知らなかったら**、「email の平均は 38 分」を、61 件全部の平均だと思って報告します。
実際には対応時間の無い 5 件が除かれていて、その 5 件がどれも長くかかった件なら、本当の平均はもっと長いかもしれません。

## 理解度チェック

1. WHERE と HAVING の違いは何ですか。

    ??? note "答え"
        WHERE は集計（GROUP BY）の前に行を絞り、HAVING は集計した後の結果を絞ります。
        「件数が 10 以上の窓口」のように、集計の結果を条件にするときは HAVING を使います。

2. 内部結合で行が減るのは、どんなときですか。

    ??? note "答え"
        右の表に、キーの合う行が無いときです。キーの書き方が違う（`K0003` と `K-0003`）だけでも合いません。
        左の行を残したいときは左外部結合を使い、相手がいなかった行の数を確かめます。

3. ある列に NULL が 5 件あるとき、`COUNT(*)` と `COUNT(列)` と `AVG(列)` はどうなりますか。

    ??? note "答え"
        `COUNT(*)` は NULL の行も数え、`COUNT(列)` は NULL を除いた数になります。`AVG(列)` は NULL を除いた値の平均です。

4. SQL に値を埋め込むとき、文字列をつなげずにプレースホルダーを使うのはなぜですか。

    ??? note "答え"
        入力が SQL の一部として解釈され、条件を書き換えられる（SQL インジェクション）のを防ぐためです。
        プレースホルダーで渡した値は、いつも「値」として扱われます。
