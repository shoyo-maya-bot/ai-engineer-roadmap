# 13-1 解答

[13-1 要件と設計書](../13-1-requirements-design.md) の演習の解答の一例です。課題 B（設計書 Q&A）を選んだ場合の例を示します。
課題 A・C でも、節の書き方は同じです。

## 1 選んだ理由

```text
課題 B（設計書 Q&A）を選ぶ。
- 08 の評価で、検索が外れた件（言い換えの質問）が残っていて、直し方を試したい
- 業務で設計書を読む時間が長く、作ったものをそのまま試せる
- 起票の承認（10）と攻撃例（11）を、自分の設計書に合わせて広げたい
```

## 2 目的と要件・構成

```markdown
## 目的と要件

- 目的: 備品貸出システムの設計書の質問に、出典つきで答え、開発者が設計書を探す時間を減らす
- 使う人: 開発者（質問する）。設計書の担当者（起票された課題を見て、設計書を直す）
- 必須:
  - 08 の設計書 4 つに、通知の設計（05-notify.md）と管理画面の設計（06-admin.md）を足して、出典つきで答える
  - 検索と生成を分けて評価し、外れた件を直す
  - 資料に答えが無く、頼まれたときだけ課題を起票する。起票は承認の係が承認する
  - 攻撃例を 5 件足して（自分の設計書に紛れた指示など）、25 件を毎回流す
- 任意: 答えの数字の裏付けの確かめ（11-1）を、答えに注意として出す
- やらないこと:
  - 設計書そのものの書き換え（起票まで。直すのは担当者）
  - PDF や Excel の取り込み（08-1 の取り込みは使わず、Markdown だけ）
  - 画面（API と curl で確かめる）
- うまくいったと言える条件:
  - 評価セット 30 件で、生成の点が 08 の版（同じ 14 件）を下回らず、追加の 16 件で 80% 以上
  - 攻撃例 25 件をすべて守れる（台本）
  - 1 件の応答時間の 95 パーセンタイルが、手元の PC で 20 秒以内

## 構成

（13-1 の本文の図と同じ。変えた所だけを書く）
- 検索: 08 のハイブリッド検索（BM25 とベクトル検索を RRF で合わせる）。追加の設計書も同じチャンク分割
- エージェント: 10 の run_agent と 11 の run_guarded をそのまま使う。system の決まりに「設計書の版（更新日）も答える」を足す
- API と配備: 12 の p12_api と compose。台数は 1
```

なぜこう書くか:

- うまくいったと言える条件は、「08 の版を下回らない（後退が無い）」と「追加分で何点」に分けました。足した設計書のせいで、前の質問が悪くなっていないかも見るためです
- やらないことに「PDF や Excel の取り込み」を入れ、範囲を Markdown に絞りました。08-1 の取り込みは、時間が余ったら任意で足します

## 3 RAG か学習か・人の承認と上限

```markdown
## RAG か学習か

- 設計書の内容（知識）: RAG で渡す。設計書は月に数回更新されるので、学習では追いつかない。出典も示す必要がある
- 答え方（形）: 07 のプロンプトの手順と例示で足りている（08 の評価で、形の崩れは 0 件）。学習はしない
- 選ばなかった方法: 設計書で LoRA を学習する（09）。更新のたびに学習し直しになり、出典も示せないため選ばない
- 見直す条件: 「出典の付け方」の誤りが、例示を増やしても評価セットの 10% を超えたら、形だけの学習（09-2）を検討する

## 人の承認と上限

- 承認なしで動くツール（許可リスト）: search_docs だけ（読むだけ）
- 承認が要るツール: create_issue。承認の画面には、題名と本文（実際の引数）を見せる。承認は 12 の /approvals（承認の係の鍵）
- 決まりで断るもの（11-3）: 頼まれていない起票・個人情報や目印を含む起票・1 回で 2 件目からの起票
- 上限（10-4）: 往復 6 回・ツール 8 回・トークン 30,000（1 件）。評価セットで測った 1 件の最大が 4 往復・約 9,000 トークンだったので、その 1.5〜3 倍
- 選ばなかった方法: 起票を承認なしで行う（勝手な起票が残るため）。上限を置かない（暴走に気づけないため）
```

なぜこう書くか:

- 上限の値に、評価セットで測った数字（最大 4 往復・約 9,000 トークン）を添えています。「なぜ 6 回か」を数字で説明できます
- 「見直す条件」を書いておくと、後で学習を選び直すべきときが分かります

## 4 題材を作る

追加の設計書の例（`05-notify.md` の一部）です。架空の内容で、08 の設計書と同じ形（見出しと箇条書き・表）にします。

```markdown
# 備品貸出システム 設計書: 通知

## 通知の種類

| 種類 | 送る時 | 送り先 |
|---|---|---|
| 返却期限の前日 | 期限の前日の 9:00 | 借りている利用者 |
| 延滞 | 期限を過ぎた翌日から毎日 9:00 | 借りている利用者と、備品の担当者 |

## 送らない場合

- 利用者が通知を止めている場合（ただし延滞の通知は止められない）
- 稼働時間外にたまった通知は、次の稼働の開始時にまとめて送る
```

考察で見ること:

- 追加の設計書には、08 の設計書と食い違う内容（例: 08 の夜間バッチは 2:00 に返却期限の通知を送るのに、こちらは 9:00）を、わざと 1 つ入れておくと、
  「どちらの資料を根拠にしたか」を出典で確かめる評価の件が作れます。食い違いは、答えで両方を示すのが正解、のように決めておきます
