# 13-3 解答

[13-3 配備・レビュー・振り返り](../13-3-deploy-review.md) の演習の解答の一例です。13-1・13-2 の解答と同じく、課題 B（設計書 Q&A）の例です。

## 1 配備の確かめ

`deploy.md` の「確かめ」の節の例です。

```markdown
## 確かめ（配備のたびに行う）

| 確かめること | コマンド | 結果 |
|---|---|---|
| 動いている | curl -s localhost:8000/healthz | 200・prompt_version（値） |
| 答えられる | curl -s localhost:8000/ask -d '{"question": "延滞の通知は何時に送られますか？"}' ... | 200・「9:00」と出典 05-notify.md |
| 承認の流れ | 起票を頼む質問 → curl .../approvals/<id>（鍵つき） | 202 → 200。鍵なしは 401 |
| 記録が残る | docker compose exec agent tail -1 /app/var/requests.jsonl | 本文なし・トークンと版あり |
| 止め方 | docker compose down → docker compose ps | 何も動いていない |
```

なぜこう書くか:

- 「答えられる」の確かめには、評価セットの 1 件（b01）を使っています。答えが分かっているので、合っているかをすぐ判断できます
- 配備のたびに同じ表を使えば、前の配備との違いにも気づけます

## 2 監視としきい値

```bash
uv run python -m roadmap_examples.p12_monitor requests.jsonl --html monitor.html --max-p95-ms 20000 --max-stopped-rate 0.1
```

しきい値の根拠の書き方の例:

| しきい値 | 値 | 根拠 |
|---|---|---|
| 応答時間の 95 パーセンタイル | 20 秒 | 13-1 の「うまくいったと言える条件」。評価セットでは（値）秒だった |
| 上限で止まった割合 | 10% | 評価セットでは 30 件中 1 件（3%）。その 3 倍を超えたら異常とみなす |

考察で見ること:

- 送った 10 件では、95 パーセンタイルは「いちばん遅い 1 件」とほぼ同じです。件数が少ないうちは、しきい値を超えても 1 件ずつ記録を見て判断します
- 最初の 1 件は、モデルを読み込む分だけ遅くなることがあります。しきい値を決めるときは、その 1 件を分けて考えます

## 4 自分で点検する

レビューの観点の表で点検した結果の例です。

| 観点 | 見つけたこと | 対応 |
|---|---|---|
| 判断の理由 | 「人の承認と上限」に、トークンの上限の根拠が無かった | 評価セットで測った最大（約 9,000）を書き足した |
| 安全 | 11-3 の誤検知の 3 件（システムメッセージなど）を確かめていなかった | 攻撃例のファイルに `benign` の件として足し、形を直した（11-3 の演習 2） |
| 個人情報と秘密 | `.env` は `.gitignore` に入っていたが、`compose.yaml` に鍵を直接書いた版がコミットの履歴に残っていた | 鍵を作り直し（古い鍵は使えなくする）、`compose.yaml` は環境変数から読む形に戻した |
| 費用 | 単価を確かめた日が書かれていなかった | `cost.md` の前提に書き足した |

なぜこう点検するか:

- 鍵がコミットの履歴に残った場合は、ファイルを消すだけでは足りません。履歴から読めてしまうので、鍵そのものを作り直して古い鍵を無効にします
- 点検で見つかった所は、レビューを頼む前に直しておくと、レビューする人の時間を、本人では気づけない所に使ってもらえます

## 5 振り返り

```markdown
# 振り返り

## うまくいったこと
- 08 の 14 件を評価セットに残したので、追加の設計書で q05 の検索が悪くなったことに、すぐ気づけた
- 攻撃例を守りなしでも流したので、追加した「決まりで断る」が効いていることを数字で示せた（守りなし 3 / 5 → 守りあり 5 / 5）

## 次に直すこと
- 言い換えの件が 9 件しかなく、検索の改善の差が偶然の範囲だった（偶然でこれ以上偏る確率 0.3）。言い換えの件を 20 件に増やしてから、並べ替え（rerank）を試す
- 応答時間の大半が、2 回目の往復（検索の結果を読んで答える）だった。検索の件数を 3 件にした版と比べる

## 数字で見た変化
| 項目 | 最初 | 最後 | 何をしたか |
|---|---|---|---|
| 生成の点（30 件） | （値） | （値） | チャンクの大きさを 08 と同じに戻した・system に更新日を答える手順 |
| 08 の 14 件 | （値） | （値。後退なし） | 同上 |
| 攻撃例（25 件・台本） | 23 / 25 | 25 / 25 | 追加の設計書に合わせた攻撃例を足し、決まりで断る係で守った |
```

考察で見ること:

- 「次に直すこと」に、数字（偶然でこれ以上偏る確率 0.3）と、次の行動（20 件に増やす）を書いています。次の人（未来の自分）が、そのまま始められます
- うまくいったことにも、なぜうまくいったか（08 の 14 件を残したから）を書くと、次の仕事で同じ工夫を使えます
