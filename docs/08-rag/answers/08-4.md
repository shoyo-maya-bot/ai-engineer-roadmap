# 08-4 解答

[08-4 RAG の評価](../08-4-rag-eval.md) の演習の解答の一例です。

## 1 評価セットに 4 問足す

```python
from pathlib import Path

from roadmap_examples.evalset import EvalCase, load_cases, save_cases
from roadmap_examples.p08_eval import DEFAULT_EVAL

MORE = [
    EvalCase(
        "u01",
        "ログインの鍵みたいなものは、どれくらいで使えなくなりますか？",
        {"sources": ["02-api.md"], "keywords": ["30 分"]},
        ("言い換え",),
    ),
    EvalCase(
        "u02",
        "借りた PC を返し忘れたら、だれに知らされますか？",
        {"sources": ["03-batch.md"], "keywords": ["備品の担当者"]},
        ("言い換え",),
    ),
    EvalCase("u03", "備品の写真はどこに保存されますか？", {"sources": [], "keywords": []}, ("資料に無い",)),
    EvalCase(
        "u04",
        "延滞中の利用者が新しく借りようとすると、API は何を返しますか？",
        {"sources": ["04-data.md", "02-api.md"], "keywords": ["借りられない"]},
        ("複数の文書",),
    ),
]


def test_extended_eval_set(tmp_path: Path) -> None:
    path = tmp_path / "qa-18.jsonl"
    save_cases(load_cases(DEFAULT_EVAL) + MORE, path)
    cases = load_cases(path)
    assert len(cases) == 18
    assert all(set(c.expected) == {"sources", "keywords"} for c in cases)
```

なぜこうするか:

- u01 は「アクセストークン」「有効期限」という資料の語を使わずに聞いています。言い換えの問いは、ベクトル検索の力を測るために要ります
- u04 は、04-data.md の「延滞中の利用者は、新しく借りられない」と、API の設計書を合わせる問いです。
  ただし、API の設計書には延滞のときのエラーコードが書かれていません。こういう「半分だけ資料にある」問いは、
  正解を「借りられない」までにして、資料に無いエラーコードを答えたら誤り、と決めておきます（決め方をメモに残す）
- `keywords` は、言い回しが変わっても入る短い語にします（「30 分」は入るが、「30 分で切れます」は入らないことがある）

## 2 diagnose のテスト

```python
from roadmap_examples.evalset import EvalCase
from roadmap_examples.llm import FakeLLM
from roadmap_examples.p08_chunk import load_chunks
from roadmap_examples.p08_eval import diagnose, eval_generation, eval_retrieval
from roadmap_examples.p08_rag import DEFAULT_DOCS, build_retriever
from roadmap_examples.p08_search import FakeEmbedder


def test_diagnose_three_kinds() -> None:
    chunks = load_chunks(DEFAULT_DOCS)
    question = "API は 1 分間に何回まで呼べますか？"
    cases = [
        EvalCase("ok", question, {"sources": ["02-api.md"], "keywords": ["60 回"]}),
        EvalCase("gen", question, {"sources": ["02-api.md"], "keywords": ["600 回"]}),
        EvalCase("ret", question, {"sources": ["03-batch.md"], "keywords": ["60 回"]}),
    ]
    retriever = build_retriever(chunks, FakeEmbedder())
    retrieval = eval_retrieval(cases, retriever, k=1)
    generation = eval_generation(cases, FakeLLM.of(["1 分間に 60 回まで [1]"] * 3), retriever, chunks, k=1)
    assert diagnose(retrieval, generation) == {"ok": "ok", "gen": "生成", "ret": "検索と生成"}
```

なぜこうするか:

- 3 件とも同じ質問にし、正解（`expected`）だけを変えています。検索の結果が 3 件で同じになるので、違いが正解の側から来ていると分かります
- 「ret」は、根拠を 03-batch.md と書いた件です。検索は 02-api.md を返すので、検索の外れになります。
  答えに「60 回」は入りますが、正しい出典（03-batch.md）を示していないので、生成の点も 1 未満です
- `FakeLLM` は、受け取った資料に関係なく決まった答えを返します。ここで確かめたいのは採点と切り分けの仕組みで、LLM の力ではないからです

| 項目 | 値 |
|---|---|
| 検索（recall@4） | （表示された値） |
| 生成（検索の結果で） | （表示された値） |
| 生成（正しい根拠を渡して） | （表示された値） |
| 外れた件と、外れた場所 | （「外れた件」の一覧） |
| 条件 | モデル名・エンベディングのモデル名・k・チャンクの大きさ |

考察の書き方の例:

- 「q10 が『検索』で外れた。資料の語は『稼働時間』『503』で、質問の『夜中』と重ならない。
  エンベディングのモデルを替えるか、01-overview.md の稼働時間の節に『夜間』という語を足すことを試す」
- 「q13 が『生成』で外れた。資料に無い承認の流れを、推測で答えた。
  システムのプロンプトの決まり 3 を、例示（資料に無い質問と『資料に記載がありません』の組）で示すことを試す」

どちらの場合も、1 つだけ変えて評価を流し直し、07-5 の `compare` で後退した件が無いかを確かめます。
