## 1 分類ごとの指標を比べる

```python
from roadmap_examples.evalset import exact_match, load_cases, run_eval
from roadmap_examples.p04_classify import DEFAULT_EVAL, DEFAULT_TRAIN, load_train, model_predict, per_class, train
from roadmap_examples.p07_classify import baseline_predict


def test_rule_is_weakest_on_bug() -> None:
    cases = load_cases(DEFAULT_EVAL)
    rule = per_class(cases, run_eval(cases, baseline_predict, exact_match("category")))
    model = per_class(cases, run_eval(cases, model_predict(train(load_train(DEFAULT_TRAIN))), exact_match("category")))
    labels = ["billing", "account", "bug", "contract", "other"]
    assert min(labels, key=lambda label: rule[label][2]) == "bug"  # F1 がいちばん低い
    assert model["bug"][2] > rule["bug"][2]
    assert model["account"][2] < rule["account"][2]  # ルールのほうが良い分類もある
```

手元の結果（F1 は小数 2 けた）:

| 分類 | ルールの適合率 | ルールの再現率 | ルールの F1 | モデルの F1 |
|---|---:|---:|---:|---:|
| billing | 0.80 | 0.67 | 0.73 | 0.77 |
| account | 1.00 | 0.83 | 0.91 | 0.80 |
| bug | 0.67 | 0.33 | 0.44 | 0.80 |
| contract | 0.60 | 0.50 | 0.55 | 0.92 |
| other | 0.50 | 1.00 | 0.67 | 0.73 |

考察の例:

- ルールベースは bug の再現率が 0.33 で、不具合の 3 件に 2 件を見逃しています。
  規則が「エラー」「真っ白」など決まった語にしか反応せず、「何も起きません」「文字化けします」のような書き方を拾えないためです
- other は再現率が 1.00 なのに適合率が 0.50 です。どの規則にも当たらない文が、すべて other に流れ込んでいます
- 正解率（66.7%）だけでは、「不具合を見逃しやすい」という、業務でいちばん困る弱点が見えません
- account だけは、ルールベース（F1 0.91）のほうが 04 のモデル（0.80）より良い結果でした。「パスワード」「認証」のような決まった語が強い手がかりになる分類は、規則でもよく当たります。
  モデルは account の文を bug・other に回していて（c009・c011）、件数の少ない評価セットでは 1〜2 件の違いで逆転します

## 2 交差検証で設定を選ぶ

```python
from sklearn.model_selection import GridSearchCV, StratifiedKFold

from roadmap_examples.evalset import exact_match, load_cases, run_eval
from roadmap_examples.p04_classify import (
    DEFAULT_EVAL,
    DEFAULT_TRAIN,
    build_model,
    load_train,
    model_predict,
    texts_and_labels,
)


def test_grid_search_on_train_only() -> None:
    texts, labels = texts_and_labels(load_train(DEFAULT_TRAIN))
    grid = {"tfidf__ngram_range": [(1, 1), (1, 2), (1, 3)], "clf__C": [0.1, 1.0, 10.0]}
    cv = StratifiedKFold(n_splits=5, shuffle=True, random_state=0)
    search = GridSearchCV(build_model(), grid, cv=cv).fit(texts, labels)  # 評価セットは使わない
    scores = search.cv_results_["mean_test_score"]
    assert max(scores) - min(scores) < 0.1  # 9 通りの差は 10 ポイント未満
    report = run_eval(load_cases(DEFAULT_EVAL), model_predict(search.best_estimator_), exact_match("category"))
    assert report.mean >= 0.8
```

手元では、いちばん良い設定は「1 文字だけ・C = 10.0」（交差検証の平均 76.9%）で、評価セットの正解率は 83.3%（25 件）でした。
既定の設定（交差検証 73.8%・評価セット 80.0%）より、どちらも少し良い値です。

なぜこうするか:

- `Pipeline` の中の設定は「部品の名前__設定の名前」（`tfidf__ngram_range`）で指定します
  （[公式ドキュメント: グリッドサーチ](https://scikit-learn.org/stable/modules/grid_search.html)）
- `GridSearchCV` は、いちばん良い設定で学習データ全体を学習し直したモデルを `best_estimator_` に入れます
- 9 通りの平均の差（68〜77%）は、各設定の標準偏差（4〜12%）と同じくらいで、「選んだ設定が本当に良い」とまでは言えません。
  評価セットでの差（1 件）も、30 件で測る誤差の範囲です。レポートには「選んだ設定は少し良さそうだが、差は誤差の範囲」と書きます

## 3 07-5 の表を 04 のモデルで埋める

方法 1 の場合:

```bash
uv run python -m roadmap_examples.p04_classify --out results-p04.jsonl
uv run python -m roadmap_examples.p07_classify --mode ollama --model <モデル名> \
    --out results-llm.jsonl --compare results-p04.jsonl
```

表の例（04 のモデルの列は手元の値。LLM の列は、使ったモデルと PC で変わるので形だけ示します）:

| 項目 | 04 のモデル | LLM（モデル名） |
|---|---|---|
| 正解率（全体） | 80.0% | （測った値） |
| 正解率（紛らわしい） | 77.8% | （測った値） |
| 正解率（指示混入） | 100% | （測った値） |
| 入力・出力のトークン数 | 0 | （測った値） |
| 費用の見積もり | 0 | ローカルは 0。クラウドの単価なら（`--price-in`・`--price-out`） |
| 時間（30 件） | 1 秒未満（学習を除く） | （測った値） |

結論の書き方の例:

- 07 の評価セットでは、04 のモデルは LLM と同じくらいか、それ以上の正解率になることがあります。その場合でも「LLM は要らない」とすぐには決めません
- 評価セットは 30 件なので、04 のモデルと LLM の差が 2〜3 件なら、誤差の範囲かもしれません（04-4 の「数字の読み方」）
- LLM は学習データを用意せずに動き、判断の理由（`reason`）も返します。新しい分類を足す、言い回しが大きく変わる、といった変化への強さも比べる観点です
- 次の一手は「評価セットに、学習データと違う人が書いた件を足して、両方を測り直す」のように、数字の弱いところを確かめる形にします

## 4 言い換えが類似度で見つからない理由

テストの `PARAPHRASES` のうち、近い組の一覧に出なかった 3 文と、元の評価セットの文です（類似度は手元で測った値）。

| 足した文 | 元の評価セットの文 | 類似度 |
|---|---|---:|
| x1: 同じ日にカードの決済が二重にされています。 | c002: クレジットカードの決済が同じ日に 2 回ありました。 | 0.41 |
| x2: 機種を変えるときの二段階認証の移し方を知りたいです。 | c009: 二段階認証の機種変更の手順を教えてください。 | 0.30 |
| x4: 支払いが負担なので、安いプランへの変更を考えています。 | c023: 支払いの負担が大きいので、安いプランを検討しています。 | 0.41 |

説明の例:

- 2 文字の組の類似度は、同じ文字の並びがどれだけ重なるかで決まります。「2 回」→「二重」、「手順を教えて」→「移し方を知りたい」のように語を言い換えると、意味は同じでも重なりが減ります
- 学習データには、話題だけが近い文（「休止の手続きはありますか。」と c020「解約の手続きはどこからできますか。」で 0.46）も多くあります。
  言い換えの類似度（0.30〜0.41）は、その中に埋もれて区別できません
- 意味の近さで測るエンベディング（08）なら見つけやすくなる可能性はありますが、それでも「同じ話題の別の問い合わせ」と「言い換え」を機械だけで分けるのは難しいままです

決まりの例:

1. 評価セットは学習データより先に作り、学習データを書く人には見せない（別の人が作る・別の時期のデータから取る）
2. 評価セットで誤った件を学習に使いたくなったら、その件を評価セットから外して学習データに移し、評価セットには新しい件を足す
3. 学習データを足したら、評価セットに近い組の上位を人が読み、評価セットと交差検証の成績の差が 30 件の誤差（7 ポイントほど）を超えていないかを見る
