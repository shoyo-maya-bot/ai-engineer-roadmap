# 04-4 解答

[04-4 指標・交差検証・過学習](../04-4-metrics-validation.md) の演習の解答の一例です。

## 1 分類ごとの指標を比べる

```python
from roadmap_examples.evalset import exact_match, load_cases, run_eval
from roadmap_examples.p04_classify import DEFAULT_EVAL, DEFAULT_TRAIN, model_predict, per_class, train
from roadmap_examples.p07_classify import baseline_predict


def test_rule_is_weakest_on_bug() -> None:
    cases = load_cases(DEFAULT_EVAL)
    rule = per_class(cases, run_eval(cases, baseline_predict, exact_match("category")))
    model = per_class(cases, run_eval(cases, model_predict(train(load_cases(DEFAULT_TRAIN))), exact_match("category")))
    labels = ["billing", "account", "bug", "contract", "other"]
    assert min(labels, key=lambda label: rule[label][2]) == "bug"  # F1 がいちばん低い
    assert all(model[label][2] >= rule[label][2] for label in labels)
```

手元の結果（F1 は小数 2 けた）:

| 分類 | ルールの適合率 | ルールの再現率 | ルールの F1 | モデルの F1 |
|---|---:|---:|---:|---:|
| billing | 0.80 | 0.67 | 0.73 | 0.91 |
| account | 1.00 | 0.83 | 0.91 | 1.00 |
| bug | 0.67 | 0.33 | 0.44 | 1.00 |
| contract | 0.60 | 0.50 | 0.55 | 0.92 |
| other | 0.50 | 1.00 | 0.67 | 1.00 |

考察の例:

- ルールベースは bug の再現率が 0.33 で、不具合の 3 件に 2 件を見逃しています。
  規則が「エラー」「真っ白」など決まった語にしか反応せず、「何も起きません」「文字化けします」のような書き方を拾えないためです
- other は再現率が 1.00 なのに適合率が 0.50 です。どの規則にも当たらない文が、すべて other に流れ込んでいます
- 正解率（66.7%）だけでは、「不具合を見逃しやすい」という、業務でいちばん困る弱点が見えません

## 2 交差検証で設定を選ぶ

```python
from sklearn.model_selection import GridSearchCV, StratifiedKFold

from roadmap_examples.evalset import exact_match, load_cases, run_eval
from roadmap_examples.p04_classify import DEFAULT_EVAL, DEFAULT_TRAIN, build_model, model_predict, texts_and_labels


def test_grid_search_on_train_only() -> None:
    texts, labels = texts_and_labels(load_cases(DEFAULT_TRAIN))
    grid = {"tfidf__ngram_range": [(1, 1), (1, 2), (1, 3)], "clf__C": [0.1, 1.0, 10.0]}
    cv = StratifiedKFold(n_splits=5, shuffle=True, random_state=0)
    search = GridSearchCV(build_model(), grid, cv=cv).fit(texts, labels)  # 評価セットは使わない
    scores = search.cv_results_["mean_test_score"]
    assert max(scores) - min(scores) < 0.05  # 9 通りの差は 5 ポイント未満
    report = run_eval(load_cases(DEFAULT_EVAL), model_predict(search.best_estimator_), exact_match("category"))
    assert report.mean > 0.9
```

手元では、いちばん良い設定は「1〜3 文字・C = 10.0」（交差検証の平均 70.0%）で、評価セットの正解率は 96.7% でした。
既定の設定と同じ値です。

なぜこうするか:

- `Pipeline` の中の設定は「部品の名前__設定の名前」（`tfidf__ngram_range`）で指定します
  （[公式ドキュメント: グリッドサーチ](https://scikit-learn.org/stable/modules/grid_search.html)）
- `GridSearchCV` は、いちばん良い設定で学習データ全体を学習し直したモデルを `best_estimator_` に入れます
- 9 通りの平均の差（66〜70%）は、各設定の標準偏差（7〜12%）より小さく、「選んだ設定が本当に良い」とまでは言えません。
  レポートには「どれも同じくらいで、既定の設定と差は無かった」と書きます

## 3 07-5 の表を 04 のモデルで埋める

方法 1 の場合:

```bash
uv run python -m roadmap_examples.p04_classify --out results-p04.jsonl
uv run python -m roadmap_examples.p07_classify --mode ollama --model <モデル名> \
    --out results-llm.jsonl --compare results-p04.jsonl
```

表の例（04 のモデルの列は手元の値。LLM の列は、使ったモデルと PC で変わるので形だけ示します）:

| 項目 | 04 のモデル | LLM（モデル名） |
|---|---|---|
| 正解率（全体） | 96.7% | （測った値） |
| 正解率（紛らわしい） | 100% | （測った値） |
| 正解率（指示混入） | 100% | （測った値） |
| 入力・出力のトークン数 | 0 | （測った値） |
| 費用の見積もり | 0 | ローカルは 0。クラウドの単価なら（`--price-in`・`--price-out`） |
| 時間（30 件） | 1 秒未満（学習を除く） | （測った値） |

結論の書き方の例:

- 07 の評価セットでは、04 のモデルは LLM と同じくらいか、それ以上の正解率になることがあります。その場合でも「LLM は要らない」とすぐには決めません
- 04 のモデルは、学習データと同じ人が書いた評価セットで測っています。交差検証の 67% を見ると、新しい言い回しには弱い可能性があります
- LLM は学習データを用意せずに動き、判断の理由（`reason`）も返します。新しい分類を足す、言い回しが大きく変わる、といった変化への強さも比べる観点です
- 次の一手は「評価セットに、学習データと違う人が書いた件を足して、両方を測り直す」のように、数字の弱いところを確かめる形にします

## 4 03 の成果物で学習し直す

```python
from pathlib import Path

from roadmap_examples.evalset import EvalCase, exact_match, load_cases, run_eval
from roadmap_examples.p03_pipeline import read_clean
from roadmap_examples.p04_classify import DEFAULT_EVAL, cross_validate, model_predict, overlap, train

CLEAN = Path("data/p03/inquiries_clean.csv")  # examples/ で実行する


def p03_cases() -> list[EvalCase]:
    df = read_clean(CLEAN)
    # 本文と分類だけを使う. response_minutes は届いた時点では分からない（リーク）ので使わない
    return [EvalCase(str(row.id), row.input, {"category": row.category}) for row in df.itertuples()]


def test_train_on_p03_output() -> None:
    cases, eval_cases = p03_cases(), load_cases(DEFAULT_EVAL)
    assert overlap(cases, eval_cases) == []
    report = run_eval(eval_cases, model_predict(train(cases)), exact_match("category"))
    assert report.mean >= 0.7
    assert cross_validate(cases).mean > 0.6
```

手元の結果:

| 学習データ | 件数 | 交差検証の正解率 | 07 の評価セットの正解率 |
|---|---:|---:|---:|
| 04 の学習データ（`data/p04/train.jsonl`） | 100 | 67.0% | 96.7% |
| 03 の成果物（`data/p03/inquiries_clean.csv`） | 130 | 73.8% | 80.0% |

考察の例:

- 03 の成果物で学習すると、交差検証は高く、評価セットは低くなりました。2 つの数字の差が小さく、新しいデータでの成績を見積もりやすいのは 03 の側です
- 04 の学習データは、評価セットと同じ判断の基準で書いた件が多く、評価セットで高く出やすい（04-4 の「数字の読み方」）と考えられます
- 学習データを替えたら、評価セットとの重なり（`overlap`）を必ず確かめます。重なりがあると、評価セットの数字は当てになりません
- `response_minutes` は 03 で整えた列ですが、対応が終わってから分かる値です。特徴量に入れると、予測のときに手に入らない情報を使うデータ漏れになります
